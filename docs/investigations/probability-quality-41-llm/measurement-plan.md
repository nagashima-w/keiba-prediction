## 1. 何を測るか

**LLM 補正込みの確率の質**を、**prior(LLM なし)と同じレース集合の対**で測る。#41 は prior だけを測った。

- ユーザー判断(2026-10-02): 「LLM で計測してもいいが、API を呼ぶのではなくサブエージェントにやらせて」。
  **実 Claude API は呼ばない(課金なし)。**
- production のプロンプト(`buildPrompt`)を、Claude Code のサブエージェントに「LLM の役」として答えさせ、
  その応答を production の `analyzeRace`(パース・`maxAdjust` のクリップ・リトライ・フォールバック)に通す。
- **事象・観測の単位・市場の作り方は #41 と同じ**: 「3着以内に入る」・出走した馬 1 頭 = 1 観測・
  市場は確定の複勝オッズ下限を Σ=3 に正規化した近似(出走 8 頭以上・確定オッズのレースだけ)。
- これは「production の LLM の質」の**近似**であって、同一ではない(§3)。

## 5. 段階 2: 応答生成(メインが行う)

### 5.1 サブエージェントの運用

- **1 レース 1 体**。他レースのプロンプトを見せない。コンテキストを使い回さない(1 体 1 レース 1 応答)。
- 汎用のサブエージェント、**モデルは最新の Sonnet**。専用のエージェント定義は作らない。
- **許すツールは「自分のプロンプトファイルの Read ちょうど 1 回」と「`SubagentHandback` 0〜1 回(Read より後)」
  だけ。** それ以外のツールは無効。応答はファイルに書かせない。メインがトランスクリプト(JSONL)から
  `scripts/probability-quality-41-llm/extract-response.ts` で応答本文を取り出し、作業ディレクトリの
  `responses/case-NN.attemptN.txt` に保存する(Write を許さないので、任意のパスへの書き込みは起きない。
  結果ファイル・Web・他のプロンプトを見る経路も、ツールを使わない限り無い)。
- **応答の取り方(実行前の改訂。応答を見てから規則を変えないよう、受理する 2 つの形を今ここで固定する)**:
  harness は、サブエージェントに「最終報告は `SubagentHandback` ツールで送る(最後に書く平文は届かない)」という
  リマインダ(`isMeta` の user メッセージ)を入れ、実際に最終出力が `SubagentHandback` の呼び出しになる
  (このセッションのサブエージェントのトランスクリプトを集計した結果、`ls *.jsonl | wc -l` の 100 件すべてに
  リマインダが入り、`SubagentHandback` の呼び出しを含むのも 100 件だった。再現: トランスクリプトの置き場所
  `~/.claude/projects/<プロジェクト>/<セッション>/subagents/` の各 JSONL を読み、`isMeta` の user メッセージと
  assistant の `tool_use`〈`name === "SubagentHandback"`〉の有無を数える。件数は実行のたびに増える)。したがって:
  - **(a) `SubagentHandback` がちょうど 1 回呼ばれた場合**: 応答は**その `input.message`**(文字列。空白だけなら無効)。
    handback より後の平文テキストは応答に数えない。`message` 以外のフィールドは**無視**する。
    handback が 2 回以上なら無効。handback が自分のプロンプトの Read より前にあれば無効。
  - **(b) `SubagentHandback` が呼ばれない場合**: 最後の tool_result より後の assistant のテキスト(連結。空白だけなら無効。
    tool_use を含めば無効)。
  - **どちらも整形しない**。前置きの散文・コードフェンスがあっても、そのまま production の `parseAnalyzerResponse` に渡す
    (production の LLM の散文と同じ扱い。パースに失敗すれば production どおりリトライ/フォールバック)。
- **検証(いずれかに反すれば、その応答は無効)**: トランスクリプトが
  (a) 自分の `case-NN.txt`(絶対パス一致)の Read がちょうど 1 回、引数は `file_path` のみ、
  (b) 上の 2 つ以外のツールが 0 回、(c) Read の結果がエラーでなくプロンプトの全文を含む、
  (d) **依頼文の定型が、最初の(`isMeta` でない)user メッセージと完全一致**(harness のリマインダは無視する)、
  (e) 応答本文が空でない(上の (a)/(b) の取り方で)。実装は `transcript.ts` の `extractFinalResponse`(テストあり)。
  あわせて、保存の前に **`subagent/case-NN.txt` の SHA-256 を `index.json` と照合する**(段階 1 の後でプロンプトが
  書き換わっていないこと)。
- **実物の形式の確認**: `build-prompts` の後、まず 1 体だけ起動し、そのトランスクリプトで抽出・検証が通ることを確かめる。
  形式(フィールド名など)が想定と違えば、その時点で合わせる。**応答の内容を見て規則を変えることはしない。**
- **無効な応答は破棄して、同じ手順で取り直す**(新しい 1 体・同じ依頼文)。無効だった件数・理由・どのレースかを
  全件レポートに載せる。取り直しは「production のリトライ」(§6)とは別物(無効な応答は試行に数えない)。
  **複数の応答から良い方を選ばない**(有効な最初の応答を採る)。
- 実行記録 `subagent-runs.json`(**抽出スクリプトが、有効・無効を問わず追記する**。作業ディレクトリに作られるので、
  リポジトリにコピーしてコミットする): ケース ID・attempt・有効か・応答の取り方(`handback`/`final-message`)・
  **モデル ID(トランスクリプトの assistant エントリの `message.model` から機械的に拾う。手書きしない)**・
  エージェント ID・開始/終了時刻・tool_use の一覧・無効の理由・応答本文の SHA-256。破棄した応答の件数と理由は、
  `valid: false` の記録から数える。

### 5.2 サブエージェントへの依頼文(定型。ファイルのパスだけが変わる)

`transcript.ts` の `renderSubagentTaskText(<case-NN.txt の絶対パス>)` の戻り値と**一字一句同じ**もの
(最初の `isMeta` でない user メッセージと完全一致しなければ、検証で無効になる):

```
次のファイルを Read ツールで1回だけ読んでください: <case-NN.txt の絶対パス>
このファイルの全文を、あなたが受け取ったユーザーメッセージとして扱い、それへの返信本文だけを最終メッセージとして返してください。
このファイルの Read 以外のツールは使わないでください。
```

最終メッセージを返す、という依頼文の文言と、harness の「`SubagentHandback` で最終報告を送る」という指示が
並ぶ。どちらの形で返しても §5.1 の (a)/(b) で受理する(依頼文の文言は変えない)。
production との差: ユーザーメッセージがプロンプト単体ではなく、この依頼文の経由になる(§3)。

## 6. リトライ(production と同じ条件で再現する)

`analyzeRace` は、(a) JSON として読めない・horses が無い・有効な補正が 0 件、(b) 印の制約違反(頭数・優先順位・
未知の印文字)、(c) 呼び出し例外のとき、同じプロンプトでもう 1 回 `complete` を呼ぶ。

- ファイル版クライアント(`file-llm-client.ts`)は「N 回目の `complete` は `case-NN.attemptN.txt` を返す」。
  応答ファイルが無いときは**例外を投げず**、「何回目が未生成か」を記録する。適用(`apply-all.ts`)は、
  `analyzeRace` から戻った後にこれを見て、**未生成のレースを pending にし、記録(`llm-observations`)を作らない**
  (集計に進ませない)。1 回目が未生成 = 応答待ち。2 回目が未生成 = 1 回目が production のパースを通らなかった。
- pending(2 回目が必要)のレースには、メインが**新しい 1 体**(同じプロンプト・同じ依頼文・別コンテキスト)を
  起動して attempt 2 を作らせ、適用を再実行する。production のリトライも独立した 2 回目のサンプルのため。
- 2 回目も失敗したら production どおり **prior に fallback**(補正後 = prior・`fallback=true`)する。
  **主表はこの挙動のまま**(fallback したレースも主表に残す)。感度として fallback のレースを除いた集計を並べる(§8.3)。
- 印の制約違反が 2 回続いた場合は、production どおり確率補正は採用し、印だけを全馬 null にする(`marksDropped`)。

## 8. 指標(実行前に固定する)

数値の算出は core の公開エントリポイント(`buildBrierQualityReport`・`buildPairedBrierComparison`)に委ねる。
中央・地方は別々に集計する。**ブートストラップ: レース単位の復元抽出・反復 10000・シード 20261001。
resolution の参照値(レース内ラベル並べ替え): 1000 回・シード 20261001**(#41 と同じ値)。

### 8.1 主表: 確率の質(prior と LLM 補正後を、それぞれ同じ 36 レースで)

`buildBrierQualityReport` を prior(`priorSource: "prior-only"`)・LLM 補正後(`"llm-adjusted"`)に 1 回ずつ。
各系列で: Brier・Murphy 分解(reliability・resolution・uncertainty・残差)・気候値に対する skill・resolution の
参照値(並べ替えの平均と 95 点)・**対市場**(出走 8 頭以上・確定オッズのレース。BS 差〈model − market〉の 95% 区間。
下限版が主表、中点版が感度。#41 と同じ)。

### 8.2 主表: LLM − prior の対の比較(同じレース集合の対。**この Issue の主眼**)

`buildPairedBrierComparison`(model = LLM 補正後、reference = prior)を次の 2 つの集合で:

- **全レース**(中央 24・地方 12)。
- **市場比較可能な集合**(中央 21・地方 12。上の対市場と同じレース集合)。

出すもの: 両系列の Brier・LLM の skill vs prior(`1 − BS_LLM / BS_prior`)・両系列の Murphy 分解・
**BS 差(LLM − prior。正なら LLM が悪い)の 95% 区間**。

### 8.3 感度: fallback したレースを除く

production の `analyzeRace` がリトライ後も失敗して prior に fallback したレースは、主表では補正後 = prior で
残る。感度として、それらを除いた集合で 8.1・8.2 を同様に出す(除外したレース ID を併記)。

### 8.4 記述統計(補正量)

- 各馬の補正量 δ = 補正後 − prior の平均(符号つき)・|δ| の平均・|δ| の最大。**fallback したレースの馬
  (補正 0・prior 採用)が主表の値に含まれる**ため、**fallback を除いた値を併記する**(`adjustment` と
  `adjustmentExcludingFallback`)。
- クリップされた馬の数(`ParsedHorseResult.clipped`)・LLM の値が使えず prior を採用した馬の数(`usedPrior`)。
- **3 着以内に入った馬と入らなかった馬での平均 δ**(補正の向きが結果と合ったか)。
- レースごとの `Σ補正後確率 − min(3, 頭数)` の中央値とレンジ(production は再正規化しない)。
- LLM の実行: fallback・印救済(`marksDropped`)・リトライ・切り詰めのレース ID。

### 8.5 記述統計(方向性: LLM の補正が市場に寄ったか。ユーザー指定で、実行前に固定する)

プロンプトには確定オッズ・人気・複勝オッズ下限が入っている(production は発走前の値)。「LLM が市場に迎合したか」
を、**市場比較可能なレース**(§8.2 の集合)の馬について出す。x = 市場含意確率(下限・Σ=3 正規化)− prior、
y = 補正後 − prior として:

- **プールした傾き**(y を x に回帰・切片あり): 1 なら市場まで寄せた、0 なら動かさなかった、負なら反対側。
- **プールした Pearson 相関**(定義できなければ null)と、**レース別の相関の中央値とレンジ**(定義できないレース数を併記)。
- **符号の一致**: y ≠ 0 かつ x ≠ 0 の馬のうち、y の符号が x と同じ(市場の方向へ補正した)馬の数・違う馬の数。
- **市場までの距離**: 馬ごとの |prior − 市場| の平均と、|補正後 − 市場| の平均(後者が小さければ市場に寄った)。

これらは**記述であり検定ではない**。区間・有意性は付けない。アンカリングの有無を断定せず、数値を並べる。

## 9. 読み方(閾値は置かない)

- **LLM の補正が確率の質を変えたか**: §8.2 の BS 差の 95% 区間が 0 を含むか。含むなら「この標本では
  prior との差を区別できない」。含まないなら向き(LLM が良い/悪い)と大きさを、prior の Brier との比で読む。
- **識別力**: LLM の resolution が §8.1 の並べ替えの 95 点を超えるか、prior の resolution と並べてどうか。
- **対市場**: prior・LLM それぞれの BS 差(model − market)の区間が 0 を含むか。
- n はレース数(中央 24・地方 12 、市場比較は 21・12)で小さい。**各セルの下位桁に意味を読まない**
  (10 帯の各帯は数件〜数十件で、reliability・resolution は小標本で偏る)。**断定しない。**
- **区間は LLM のサンプリングのばらつきを含まない**(§3)。区間が 0 を含まなくても、別の回の応答では
  結論が変わりうる。
- 結論を「#35-2/#42 に進む/進まない」と書く場合は、**サブエージェントが production の LLM と同一でない近似**
  であること(§3)、確定オッズがプロンプトに入っていること、標本が小さいことを併記する。
- 方向性(§8.5)の数値から「迎合した」「しなかった」と断定しない。
