## 2. 中央: 取得経路の確定

### 2.1 type値の独立観測(#1)

`race.netkeiba.com/odds/odds_get_form.html?type=b3&race_id=...` フラグメント内の埋め込みJS
(`$.oddsUpdate({...})`)から、数値type値を独立観測した(#13・#103・#127と同じ手続き。
番号を推測していない):

```
grep -o "oddsType:'[0-9]*'" fixtures/odds_get_form_b3_202603020211.html
→ oddsType:'3'
```

既存の JSON API(`race.netkeiba.com/api/api_get_jra_odds.html`)と**同一エンドポイント**の
`type` クエリを変えるだけで取得できることを実測で確認した(#2・#3・#10)。

### 2.2 確定オッズの実データ構造(#2・#3・#10)

3レースで取得した応答を `wakuren-odds-fixtures.test.ts` で検証した。**期待集合は枠の構成
(出馬表・結果テーブルの枠番)から計算した**もので、オッズ側のキーから頭数を逆算していない:

| レース | 頭数 | 枠の構成(枠→頭数) | 期待キー数 | 実測 | 頭数・枠の情報源 |
|---|---|---|---|---|---|
| 202603020211 | 16 | 8枠すべて2頭 | 28+8=**36** | 36件で完全一致 | `parseShutuba(fixtures/shutuba_202603020211.html)` |
| 202602010607 | 10 | 7・8枠のみ2頭 | 28+2=**30** | 30件で完全一致 | `parseShutuba(fixtures/shutuba_202602010607.html)` |
| 202607020501 | 9 | 8枠のみ2頭 | 28+1=**29** | 29件で完全一致 | `parseRaceResult(fixtures/result_202607020501.html)`(AC-A8。§9) |

- **キー形式**: 4桁(**枠番**2桁×2)。**昇順**連結(`"0407"`。逆順 `"0704"` は存在しない)。
- **値の型**: `[オッズ, "0.0"(ダミー), 人気]` の**単一値**(下限・上限を持たない。馬連・馬単・3連複・三連単と同じ形。
  ワイドtype=5のような幅ではない)。16頭の36件全件で2要素目が `"0.0"`。
- **組合せ集合の式**: 異なる2枠の組合せ C(枠数,2) に、**2頭以上が入る枠に限り**同枠(`AA-AA`)が加わる。
  期待キー数 36/30/29 は3レースとも計算値と実測が一致した。**組合せは馬番ではなく枠番**であり、
  頭数(16・10・9)に依存せず**枠数は8**(本タスクで検証した9頭以上の5レース〈中央3・地方2〉すべて)。
- **同枠の買い目(AC-A4)は実在する**: 16頭で `0101`〜`0808` の8件、10頭で `0707`・`0808` の2件、
  9頭で `0808` の1件。1頭だけの枠には同枠キーが**無い**(10頭で `0101` は存在しない)。

`GET https://nar.netkeiba.com/odds/index.html?type=b3&race_id={race_id}` の**静的HTML**。
セルの id は `chk_{…}_b3_c0_{枠}_{枠}`(例 `chk_a1-54-10_b3_c0_5_6`。枠番は1桁表記・昇順)、
テキストがオッズ(単一値。例 `10.7`)。

## 5. AC-A3: 発売される頭数の境界

**根拠は確定払戻ページの `tr.Wakuren`(枠連の払戻行)の有無**(発売されていれば払戻行がある)。頭数は結果テーブルの行数。

| 頭数 | 中央 | 地方 |
|---|---|---|
| 5 | 枠連行なし(202603020203。既存) | 未確認 |
| 6 | 枠連行なし(202602010605。既存) | 枠連行なし(202646071203。既存) |
| 7 | **枠連行なし**(202607020502。新規) | 枠連行なし(202630062407。既存) |
| **8** | **枠連行なし**(202607020505。新規) | **枠連行なし**(202654092711。新規) |
| **9** | **枠連行あり**(202607020501。新規。1-8=550円) | **枠連行あり**(202654092706。新規。3-8=760円) |
| 10 | 枠連行あり(202602010607。既存) | 未確認(202654071201 の一覧上の頭数は10だが結果テーブルでは確認していない。枠連行はある) |
| 12 | 未確認 | 枠連行あり(202654071210。既存) |
| 16 | 枠連行あり(202603020211。既存) | 未確認 |

**結論(観測した範囲)**: 中央・地方とも **8頭以下は枠連の払戻行が無く、9頭以上は払戻行がある**。
ユーザーの記憶は「8頭未満」か「7頭未満」で揺れていたが、**どちらとも一致しない**(8頭でも発売されていない)。
- **各頭数の標本は1レースずつ**(8頭・9頭は中央・地方とも1レースだけ)。8頭・9頭を「必ず」と外挿しない。
- 頭数が枠数(8)を超えて同じ枠に2頭が入り始める(枠と馬番が乖離し始める)のが9頭であり、発売の開始と一致する。
  ただしこれは観測の一致であって、netkeibaが同じ理由で線を引いていることの確認ではない。

再現手段: 頭数と枠連行の有無の対応表は `wakuren-odds-fixtures.test.ts`
「発売の頭数境界」describe が全12ファイルで固定している
(`pnpm --filter @keiba/core exec vitest run test/scraper/wakuren-odds-fixtures.test.ts`)。

## 6. 発売条件の状態(②発売なし)のオッズ応答形状

頭数不足(7・8頭)で枠連が売られないレースの応答は、中央と地方で形が違う。

### 6.1 中央(#6・#8): **presale(未発売)と区別できない封筒**

7頭・8頭とも `type=3` の応答は次の80バイトで、2本は**バイト一致**した:

```json
{"status":"NG","data":"","update_count":"0","reason":"empty free odds schedule"}
```

これは #103 が観測した中央presale(未発売)の封筒(`odds_wide_presale_202604020511_20260806.json`・
`odds_trio_presale_202604020511_20260806.json`)と**バイト一致**する
(`cmp fixtures/odds_wakuren_unsold_202607020502.json fixtures/odds_wide_presale_202604020511_20260806.json`
が差分なしで終わる)。**応答の封筒だけでは、「頭数不足で売られない」と「発走前でまだ売られていない」を
区別できない。**

### 6.2 地方(#12・#15): **通常の発売ページ構造のまま、枠連セルが全件 `0.0`**

7頭(202630062407)・8頭(202654092711)とも:
- `#odds_select` が存在する(**presaleのフォールバックとは異なる**。#13・#103・#127のpresaleは `#odds_select` が無く、
  組合せセルが0件だった)
- 枠連セル(`chk_..._b3_c0_`)が**28件**(=C(8,2)。**頭数7でも8枠ぶん**。同枠のセルは無い)あり、
  **値はすべて `0.0`**(28件全件)
- 頭数7でも `0708`(7-8枠)のセルがある = 実在しない枠のセルまで含めた8枠固定のテンプレート

**⚠️ 現行のオッズ数値化(`toOddsNumber`)は値域を課さない設計**(`odds-number.ts`のJSDoc参照)ため、
この `0.0` を素直に読むとオッズ0の組合せ28件が出来うる。**#26-B(パーサ)の実装時に、`0.0` を
オッズ欠損として扱うかを決めること**(本タスクでは未検証。パーサを触っていない)。

再現コマンド(AC-A7):

```
cmp fixtures/odds_wakuren_unsold_202607020502.json fixtures/odds_wakuren_unsold_202607020505.json && echo 一致
for f in nar_odds_b3_unsold_202630062407 nar_odds_b3_unsold_202654092711; do
  grep -o 'id="chk_[^"]*_b3_c0_[0-9_]*"' fixtures/$f.html | sort -u | wc -l                          # => 28
  grep -o 'id="chk_[^"]*_b3_c0_[0-9_]*"[^>]*>[^<]*' fixtures/$f.html | sed -E 's/.*>([^<]*)/\1/' | sort | uniq -c   # => 28 が 0.0 と 28 が空(input側)
done
```

## 7. presaleは取得していない

presale(発走前)の追加リクエストはしていない(ユーザー判断 2026-09-29)。理由: 未発売時のフォールバックが
券種によらず同一であることは #13・#103・#127 で確認済みで、枠連で確かめ直す価値より
netkeibaへの負荷を減らすことを優先した。**枠連のpresaleは未確認**(上記フォールバックが成り立つはずだが、
本タスクでは観測していない)。§6.1の通り、中央では頭数不足の応答がpresaleと同一封筒だったため、
少なくとも中央の「presaleとの区別」は封筒からは付かない。

## 12. 後続の子Issueへの申し送り事項

1. **枠連のキーは馬番ではなく枠番。** 馬番→枠番の対応(出馬表の `wakuban`)が要る。オッズキーは
   `AABB`(昇順)、地方は id 末尾 `_{枠}_{枠}`。
2. **期待キー集合の式**は C(枠数,2) + (2頭以上の枠の数)。同枠キー(`AA-AA`)は**実在する**。
   同枠の値の払戻突合は未検証(§8.1)。
3. **1リクエストで全組合せ**(中央・地方とも。§4)。取得の配線は馬連と同じ形で済む見込み。
4. **発売条件は9頭以上**(観測。各頭数1レースずつ。§5)。「8頭未満/7頭未満」というユーザーの記憶とは一致しない。
   8頭以下のレースでは、中央は封筒 `NG`(presaleと同一)、地方は全セル `0.0` の28件が返る(§6)。
   **地方の `0.0` をオッズとして読まないこと**を#26-Bで決める(§6.2)。
5. **同枠買い目の的中確率**は、その枠に属する馬が1着・2着に入る組合せの合算になる。
   枠連の的中確率(枠に属する複数頭の合算、および同枠は、定義上、上位2頭がともにその枠の馬になる確率)の
   設計は後続の子Issueの責務で、本タスクは扱っていない。
6. **枠単は未調査**(§8.2)。本タスクでは取得していない。
7. `"wakuren"` という語は本ドキュメント・フィクスチャファイル名限定の命名であり、
   `AllocationBetType` 等のメンバー名は後続の子Issueで別途決定すること(§0)。
