## 2. 中央: 取得経路の確定

### 2.1 type値の独立観測(#1・#6)

`race.netkeiba.com/odds/odds_get_form.html?type=bN&race_id=...` フラグメント内の
埋め込みJS(`$.oddsUpdate({...})`)から、数値type値を独立観測した(#13と同じ手続き。
番号を推測していない):

- 馬連フラグメント(`type=b4`)の埋め込みJS: `oddsType:'4'`(#1のフィクスチャから
  `grep -o "oddsType:'[0-9]*'" fixtures/odds_get_form_b4_202603020211.html` で再現可能)
- 馬単フラグメント(`type=b6`)の埋め込みJS: `oddsType:'6'`(同様に
  `fixtures/odds_get_form_b6_202603020211.html` から再現可能)

既存の単勝・複勝/ワイド/3連複JSON API(`race.netkeiba.com/api/api_get_jra_odds.html`)と
**同一エンドポイント**の`type`クエリを変えるだけで取得できることを実測で確認した(#7, #9)。

### 2.2 確定オッズの実データ構造(#7・#9)

16頭・確定レース(race_id=202603020211。#13で使用した既存対象と同一。頭数は
`parseShutuba(fixtures/shutuba_202603020211.html).horses.length===16`から独立に確認済み)で
取得した応答を`packages/core/test/scraper/quinella-exacta-odds-fixtures.test.ts`で検証した:

- **馬連(`data.odds["4"]`)**: キー集合が**C(16,2)=120件**と完全一致(順不同。逆順キー
  `"0201"`は存在しない。`fixtures/odds_quinella_202603020211.json`)
- **馬単(`data.odds["6"]`)**: キー集合が**P(16,2)=240件**と完全一致(順列。`"0102"`と
  `"0201"`が**両方**存在し、**値が異なる**。前者124.4・後者135.5。`fixtures/odds_exacta_202603020211.json`)
- いずれも値形式は`[オッズ, "0.0"(ダミー), 人気]`の**単一値**(下限・上限を持たない。
  既存の単勝type=1・3連複type=7と同じ形。ワイドtype=5のような幅ではない)
- キー形式: 4桁(馬番2桁×2)。馬連は昇順連結・馬単は**着順(1着→2着)のまま連結**(ソートしない)

### 2.3 中央の結論

- **経路**: JSON API `GET https://race.netkeiba.com/api/api_get_jra_odds.html?race_id={race_id}&type={4|6}&action=init`(既存`oddsApiUrl`と同一メカニズム)
- **1レース分の全組合せに必要なリクエスト数**: **1**(馬連・馬単とも)
- **馬連は組合せ(C(n,2))・馬単は順列(P(n,2)=組合せの2倍)**。中央16頭で実測: 馬連120件・馬単240件

## 3. 地方: 取得経路の確定

### 3.1 馬連(type=b4、#10)

`GET https://nar.netkeiba.com/odds/index.html?type=b4&race_id={race_id}` の**静的HTML**
(12頭、race_id=202654071210。#13で使用した既存対象と同一)。

- `td.Odds[id^="chk_"][id*="_b4_c0_"]`が**66件=C(12,2)と完全一致**
- 単一値形式(例: id `..._b4_c0_1_2`のテキストは`"147.4"`。ハイフン区切りの幅表記なし)

### 3.2 馬単(type=b6、#11)。**軸馬機構は不要と判明(3連複との対比が重要)**

`GET https://nar.netkeiba.com/odds/index.html?type=b6&race_id={race_id}` の**静的HTML**
(同一レース、12頭)。

- `td.Odds[id^="chk_"][id*="_b6_c0_"]`が**132件=P(12,2)と完全一致**。**1リクエストで
  順列すべてが返った**
- `(1,2)`(id `..._b6_c0_1_2`)="328.4"、`(2,1)`(id `..._b6_c0_2_1`)="232.9"と、
  **逆順ペアが別セルとして異なる値を持つ**ことを実データで確認(単一値形式)

**⚠️ #13で確立した「地方3連複は軸馬別取得(`jiku`パラメータ、n-2回のリクエストが必要)」
という知見を馬単にそのまま外挿してはならない。** 実測の結果、地方馬単は3連複と異なり
**軸馬機構を必要とせず、1リクエストで全順列P(n,2)が返った**(§4でAC-A2として再掲)。
**なぜ3連複だけ軸馬別で、馬連・馬単は1リクエストで済むのかは、今回の実測範囲では
分かっていない。理由を推測で書かない**(観測されたのは「馬連・馬単は1回、3連複は
軸馬別」という事実のみ)。

### 3.3 地方の結論

|---|---|---|---|
| 馬連 | 静的HTML(`type=b4`、軸馬クエリ不要) | **1** | 単一値 |

## 4. AC-A2: 1レース全組合せに必要なリクエスト数のまとめ

**馬連・馬単とも、中央・地方とも「1」。** 地方3連複(n-2回、軸馬別取得)とは異なり、
本タスクの範囲(頭数12・16の各1レース)では軸馬別取得が不要だった。

**この発見は#24全体のスコープ見積もりを下げる。** 地方3連複だけが特殊(軸馬別)であり、
馬連・馬単は中央・地方とも「1リクエストで全組合せ」という中央ワイド・中央3連複・地方ワイドと
同じ単純な形に収まる。

## 5. AC-A3: 馬単のキーが順序付きであることの証拠

「同じ2頭の逆順が別エントリとして異なる値を持つ件数」を無条件`expect`で固定した
(`packages/core/test/scraper/quinella-exacta-odds-fixtures.test.ts`)。

- **中央(16頭、P(16,2)=240件)**: 240件全件を走査し、逆順ペアが存在してかつ値が異なる件数が
  **240件**(=全件)であることを固定
- **地方(12頭、P(12,2)=132件)**: 132件全件を走査し、同様に**132件**(=全件)が異なる値を
  持つことを固定

両方とも「1組だけ違う」ではなく**全件が異なる**ことを確認しており、退化していない。

## 7. 400はnetkeiba側の一過性スロットルであり、type・エンドポイントに依存しない(UAは恒久的拒否のみ否定)

本タスク実施中、400を計11本受けたが、**いずれも同一URLへの再試行(間隔を空けるだけ)で
最終的に200へ転じている**(UAは`DEFAULT_USER_AGENT`のまま一度も変更していない)。
以下は本ドキュメントの範囲内(§1の発火ログ)だけで再現できる根拠:

- **#2〜#6**: 同一URL(中央・馬単typeフラグメント)に対し、400→400→400→400→**200**
  (間隔0秒→8秒→15秒→30秒で最終的に成功。§1参照)
- **#8〜#9**: 同一URL(中央・馬単確定オッズJSON)に対し、400→**200**(8秒間隔)
- **#13〜#14**: 同一URL(地方presale探索用race_list_sub)に対し、400→**200**(8秒間隔)
- **#15〜#20**: 同一URL(地方・馬連presaleページ)に対し、400×4(0→8→15→30秒)→
  (診断#19を挟んで)→**200**(単発再試行)

**typeへの依存を否定する根拠**: #1(`type=b4`)は初回から200だったのに対し、#2(`type=b6`、
同一エンドポイント・同一レース・直後の呼び出し)は400だった。逆に#7(`type=4`)は初回から
200、#8(`type=6`)は400から始まっている。**同じtype値でも成功・失敗どちらも観測されており、
特定のtype値が恒久的に拒否されているわけではない**(#4〜#6で`type=b6`のフラグメントは
最終的に200を得ている)。

**UAへの依存を否定する根拠**: 本タスクの全22発火は`HttpClient`の既定UA
(`DEFAULT_USER_AGENT`。`packages/core/src/scraper/http-client.ts`)を一度も変更せず使用した。
UAを一切変えていないにもかかわらず、同一URLへの再試行だけで400→200が再現しており、
**UAによる恒久的な拒否は否定された。UAがスロットル閾値に影響するかは本タスクの観測では
判別できない**(非ブラウザUAだとスロットル閾値が低い〈成功はするが早く詰まる〉という形の
関与は、本タスクのデータからは排除できない。この変数は#104で別途扱う)。

**⚠️ 一般化の範囲について**: 本タスクの実行環境はクラウドサンドボックスの共有エグレスIPで
あり、netkeiba側のスロットリングがこのIPレンジに対して特に敏感である可能性を排除できない。
**「利用者の実機でも同じ挙動になる」とは一般化しない**(配布exeが利用者の環境でnetkeibaに
どう見えるかは、本タスクのスコープ外・別Issue〈#104〉で扱う)。

**再試行の実装**: `scripts/fetch-quinella-exacta-raw.ts`が、400を受けた際に
8秒→15秒→30秒のバックオフで同一URLを最大3回再試行するロジックを内蔵している
(JSDoc参照)。403/429は性質が異なる可能性があるため再試行せず即座に報告する設計にしている。

## 10. #24-Bへの申し送り事項

1. **馬連・馬単とも、中央・地方いずれも1リクエストで全組合せが取得できる**(§4)。3連複のような
   軸馬別取得の実装は不要
2. **馬単のキーは着順を保持したまま(ソートしない)扱う必要がある。** 既存の`buildComboOddsKey`
   (`packages/core/src/scraper/combo-odds-key.ts`)は昇順ソートするため、そのまま馬単に流用すると
   着順情報が失われる(本ドキュメントのテストが自前の`expectedOrderedPairKeys`を持つ理由)
3. **中央presaleの4状態確認は未達成のまま**(§6.2)。#24-B着手前に必要であれば追加調査を検討する
4. `"quinella"`/`"exacta"`という語は本ドキュメント・フィクスチャファイル名限定の命名であり、
   `AllocationBetType`等のメンバー名は#24-Bで別途決定すること(§0)
