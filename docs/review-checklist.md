# レビューの観点集

`.claude/agents/code-reviewer.md` から走査の観点を移した文書である(Issue #606)。観点は、過去のレビューですり抜けた欠陥から積み上げた。レビュー担当は、差分の種類に合う節だけを読む。
Issue #609 で、重複する観点をまとめ、手順と事例の経緯を縮めた。書き直す前の観点の一覧と、まとめた・消したものの対応は `docs/investigations/review-checklist-inventory.md` にある。

## この文書の使い方

- 観点は「見つけ方」であって「止める基準」ではない。見つけたら、CLAUDE.md「★ブロッキングの基準」の 3 区分で【要修正】か【記録】かを決める。
  - 【要修正】にしてよいのは、(1) 利用者から見える誤り、(2) production から到達できる契約違反、(3) クラッシュ・データ破損、の 3 つだけである。
  - 散文(JSDoc・コメント・テスト名)の不正確さ、到達できない経路のテスト不足、数値として無害な変異の生存、命名や好みは【記録】である。
- 本文の「指摘する」は、観点に当てはまったという意味である。区分は上の基準で決める。
- 「変異注入」は、守りたい挙動を壊す変更を実装に入れて `pnpm test` を流し、赤くなるかを見ることである。「全緑」は、その変異を入れても全テストが緑のままという意味である。検出力は、読んで論証せず、変異を入れて自分で確かめる。
- 事例の `boss` は、2026-09-24 に廃止した旧役割である(着手前ゲートとメタレビューは、いまメインセッションが担う)。事例は経緯の記録なのでそのまま残す。

## 基本の観点

- **仕様適合**: `docs/current-spec.md`(現状仕様。`keiba-ev-tool-spec.md` は当初計画の記録)の該当箇所と突き合わせ、乖離・解釈違いがないか。
- **TDDの形骸化**: テストが実装の写しになっていないか。境界値(サンプル不足時の補正なし等)があるか。失敗しうる意味のあるアサーションか。
- **正確性**: 計算の誤り、off-by-one、null/undefined の処理、日付・レース間隔の計算。
- **スクレイパーの堅牢性**: セレクタの集約、取得失敗時のフォールバック、レート制限の遵守。
- **規約**: コメント・ドキュメント・テスト名が日本語か。
- **保守性**: 過度な複雑さ、重複、責務の混在。

## ユーザー向け説明文と実出力

- **1対1で照合する**: 「実際に何が起きるか」を説明する UI の文言(注記・プレビュー・ヘルプ)は、対応する実出力(プロンプト文面・生成物)の全条件分岐を洗い、矛盾がないか照合する。「このまま送られる」の断定は、条件付きの要素(天候・馬場の分岐、未保存入力と保存済み値の差、欠損時の表記)を見落としやすい。実出力は tsx 等で実際に生成して突き合わせる。
- **原因を名指しする文言**(「〜の制約により」)は、出る全経路で原因が真かを、条件が成立する入力を複数通り走らせて実測する。フラグの計算の正しさと、添えた原因説明の正しさは別の検証である。core が原因を書いていないフラグに renderer が原因を足していないか、文言のテストが出現順・件数だけで内容の真偽を見ていないかも疑う。(C-2: 上限が効かない経路〈丸め・最低額〉でも「1レース上限の制約により」と出た)

## 新経路・並行する系での継承

- **新経路の表示要素**: 同じ画面領域を描く別経路を横に足す変更(券種・モードの追加)では、何も削除していないのに、既存経路の注記・警告だけが新経路に無いことがある。既存経路が描く要素(テーブル・合計行・条件付き注記・固定注記)を全数列挙し、新経路の同じ状態に対応する要素があるかの表を作る。「無い」セルは、出さない理由が JSDoc にあるかを見る。共通ヘルパーを使わず自前で組み直している箇所を疑う。型の非互換が理由なら、元データが呼び出し側に残っていないかを確認する。(D-2c 第4段: 混在経路だけ確率合計警告が無く、current-spec は「警告を出す」と書いたままだった)
- **並行する 2 系の欠損値**: 同じ結果テーブルを別の規則で集計する系を足す差分は、`null`・未取得・対象外の扱いが抜けやすい。入力の各フィールドの欠損しうる値を列挙し、「既存系 / 新系 / 違いが書かれているか」の表を作る。違いが実装にしか無ければ指摘する。(#71: 新系が取消・除外馬を不的中として分母に積み、回収率を下振れさせた。既存系は集計対象外と明記していた)

## 欠陥クラスの水平展開

バグを 1 件見つけたら、同じ失敗モードが他の入力・フィールドに無いかを全数で洗い、最初のレビューで一度に報告する。1 箇所だけ指摘すると、同種の残りが次の周で出る。(C-1: 「未判定を判定結果として報告する」欠陥と「設定値の無防御による NaN の漏れ」が、3 周連続で別フィールドから再発した)

- **数値の異常値注入**: 入力の防御漏れを見つけたら、その関数の設定オブジェクト/引数の全数値フィールドに `NaN`/`±Infinity`/負値/0/範囲外/非整数を注入し、出力が有限で契約を守るかを表で確かめる。配列・Map の要素の中の数値も含む(1 件の `NaN` が、無関係な健全要素の計算まで壊すことがある)。構造の検証(並び・重複・空)があるのに数値の検証が無い非対称や、防御した値としない値の同一関数内の混在は、それ自体を指摘する。(D-2a: 候補の `odds` の `NaN` で、健全候補の配分まで消え、誤った見送り理由が出た)
- **説明系フィールドと状態対応表**: 理由文言・分類フラグ・診断値の誤りを見つけたら、同じ結果オブジェクトの他の説明系フィールドが、その値の算出経路を実際に通ったかを確認する。JSDoc の「`undefined` なら未取得」「`{}` なら発売なし」のように状態と原因を 1 対 1 にする記述は、その状態を作る全経路を実装から洗い、本当に 1 対 1 かを確認する。違うなら、原因を判別するフィールドを明記させる。(D-2c 第1段: 「`{}` = 発売なし」と書かれたが、取得失敗でも `{}` になった。同じ差分の別の JSDoc の誤りを直させたあと、同種の記述を走査せずに LGTM を出した)
- **列挙値・文言定数のドメイン**: `switch`/`Record`/`includes` で分岐する対象は、取りうる値の全集合の表を作り、各値について戻り値が値として固定されたテストがあるかを埋め、空白セルに変異を注入する。未知値へのフォールバックも含める(最も試されにくい)。(#55: 同じ欠陥クラスが 3 ラウンドに分かれて出た。`"unknown"` はテスト入力に一度も使われていなかった)
- **多分岐の最終 else**: `if (A) … if (B) … else return C` は、A でも B でもない入力に C を断定し、壊れた DB 行や旧データで利用者に偽の断定を出す。最終分岐(`else`・`??`・`? :`)が判定結果(理由・原因・ラベル)を返す箇所で、落ちる入力が 1 種類しか無いかを型と実装から数える。2 種類以上なら、「判定できない」を述べる別の出力を用意させる。同じモジュールの他の想定外入力に専用フォールバックがあるのにここだけ断定している非対称は、強い兆候である。(#55: 総資金も上限も 0 より大きい記録に「1レースの上限が0円のため…」と返した)

## テストの空振り

- **分岐内のアサーションと自明な成立**: `if (...) { expect(...) }` は、前提が成立するかを実際に実行して実測値で示し、前提は無条件 `expect` で分岐の前に固定させる。分岐が無くても、差・上界のアサーションは左辺が常に 0 で自明に成立しうる。テスト名が「差」「剰余」「上界」を名乗るなら、その差が 0 でないことを先に固定する。実測値が境界から桁違いに離れているのは、余裕ではなく現象が起きていない証拠であることが多い。「成立したか」ではなく「検証対象の現象が起きたか」を問う。1 頭集中・`betCount===1`・`Σx*` が 1.0 や 0 に張り付く退化入力は貪欲最適化で頻出するので、多点配分を前提とするテストは `betCount` を固定する。(C-1: `if (betCount >= 2)` が実測 `betCount = 1` で常に偽だった。C-2: 剰余の再配分のテストが退化配分になり、丸めが一度も起きなかった)
- **禁止事項の不在**: `.toBe(false)`/`not.toContain`/`not.toMatch` のように何かが無いことを主張するテストは、検出器(正規表現・キーワード)側を壊すだけで永久に緑になる。検査される側にだけ変異を入れても、検出器が生きている証拠にならない。検出器が真を返す入力を固定したテスト(正の対照)があるかを探し、無ければ、過去に実際に問題だった文字列(`git show <事故コミット>:<パス>`)を `toBe(true)` で固定させる。検出器自体に変異を入れて全緑なら、その不変条件は実質存在しない。(#43)

## テストの検出力(変異注入)

- **ソース走査テスト**: 識別子・文字列がソースに現れることの検査(`toContain("display.foo")`)は「書かれている」であって「使われる」ではない。`push` の行だけを消しても `if` 行に同じ識別子が残り、通る。振る舞いテストの代替として認めず、組み立てロジックを純関数に切り出して戻り値を直接 assert する形を求める。変異は最小の単位で入れる(ブロックごとの粗い変異で落ちても、細かい変異で落ちる証拠にならない。実装者の「壊して失敗を確認した」は、どの粒度かを聞く)。(D-2c 第4段: `notices.push(...)` の 1 行削除が素通りした)
- **対になる 2 状態と fail-open**: 「キーあり値 `null`」と「キーごと不在」のように 2 状態を区別する契約は、片側だけのテストでは、もう一方へ退化させる変更(`null` を落とす・空配列を `undefined` に丸める)を検出できない。それぞれの状態を作る入力のテストを探し、無い側を潰す。対は分岐と条件式の真偽にもあり、「全分岐 × 新しく足した情報の有無」の表で空セルを 1 つずつ潰す。変異は、条件を置き換える向き(`A`→`B`)だけでなく、選言で広げる向き(`A`→`A || B`)も試す。広げる変異は、`B` が真の状態で「その出力が現れないこと」を主張するテストが無ければ素通りする。空セルを「他のセルで守られている」という論証で埋めない。(#33: `unfetched` 側だけがテストされていた。D-2c 第1段: 残り 2 セルを論証で埋めたが、`|| wideCombo !== undefined` を足す変異が全緑だった)
- **演算子の極性**: 設定ファイル・ワークフロー・条件式を文字列で検査するテストは、`toContain` による存在確認では演算子の反転(`!=`→`==`、`&&`→`||`、否定の有無)を検出できない。破壊で検証したと報告されたら、極性反転を含むかを見る。(CI のスキップ通知の条件を反転しても 6 件全緑だった)
- **新設分岐が既存ロジックの複製**: 新しい経路を足す差分は、既存の判定式を書き写した第 2 の実装を生みやすい。赤くなるのは既存側の 1 本だけで、複製側は無防備になる。新設分岐の述語・集計式と同じ式が既存経路に無いかを grep し(`every`/`some`/`filter`)、複製側だけを変異させて該当パッケージ全体の `pnpm test` を流す。複製は `=== 0`/`=== Infinity` のような値による場合分けとしても現れるので、`buildX` ↔ `buildOrderedX` のような対の関数は、新設側の全分岐を列挙して、各分岐を通すフィクスチャが実在するかを埋める(既存側に専用の集合〈`zeroSet`・未知値・空〉があるのに新設側のフィクスチャにその値が無い形は強い兆候)。分岐を通すフィクスチャが、その分岐の読む他の集合について退化していないか(常に空/常に全件)も、分岐軸×分類の 2 次元の表で見る。「出力を検査するテストがある」は根拠にならず、`toBeGreaterThan(0)`・`Number.isFinite(x)` のような述語検査は検出力の要件を満たさない。(#92: 的中判定の `every` を複製した新経路で、`every`→`some` でも全緑のままワイドの的中確率が 13 倍に化けた。θ 分類の複製では `placeProb: 0` のフィクスチャが無く、θ=0 の変異が全緑だった)
- **配り先と呼び出し元**: 1 つの束縛(フラグ・判別結果)を複数の消費点へ配る差分、または共通関数に新しい引数を通して 2 つ以上の経路から呼ぶ差分は、出現箇所の grep では検出力を証明できない。読み手(呼び出し元)を全数列挙し、読み手ごとにその 1 箇所だけを別の値(引数なら定数)へ差し替える変異を注入して、全緑の読み手があれば指摘する。「1 つが固定されていれば足りる」は、全部を一斉に壊す変異にしか効かない。合算一致の不変条件テストも、新しい引数が分岐を変える組合せをフィクスチャが踏んでいなければ穴を塞がない。読み手が 0 個のフィールド(core で計算して View 型まで配線したのに UI が読まない値)も指摘する。(#70: 読み手 4 箇所のうち 2 箇所が全緑。#71: 分母から落とした買い目の点数が画面に出ず、「ワイド0点」の意味を区別できなかった)
- **既定値の切替**: 検出力の欠落は `not.toBe(旧既定)` の形に限らない。(i) 新既定と食い違わなくなる、(ii) 肯定形の `toBe(リテラル)` が偶然新既定と一致する、(iii) 検査するテストが無い。(ii)(iii) は grep では見つからない。切り替えた値を読み出している production の全箇所(切替点でなく読み出し点。テスト側も全パッケージ)を列挙し、各箇所で引数を無視して新既定/旧既定をハードコードする変異を入れて、赤が 0 本なら指摘する。「同型の欠陥は他に無い」と言う前に、列挙が網羅的であることを示す。既定が変わると空振りする `not.toBe(旧既定)` も、新既定を代入して落ちるかを確かめる(コメントを直しても検出力は戻らない)。(#81/#86: 全数走査 0 件を根拠に「同型は無い」と報告されたが、`allocateGeneralBets` の `modelId` をハードコードする変異が全緑だった。boss の「検査するテストが無い」も、走査を 1 ファイルに限った誤りだった)
- **先送りの根拠と検出力の断定**: 陳腐化しかけた記述を次の Issue へ送る判断は正当だが、根拠が「将来 ◯◯ を触れば自動的に赤くなる」なら、それは検証可能な断定である。その変更を今注入し、赤になるファイルと緑のままのファイルを列挙する。反対向きの断定(「このテストでしか検出できない」「唯一」「原理的に検出不能」)も、他のテストが赤くならないことを変異で確かめるまで受理しない(`しか検出できない`/`原理的に`/`唯一` で grep)。是正すべきは断定の方で、テストは消させない。(#91: 注入した変異に `verify-format.test.ts` は全緑〈`verify.ts` を通らない〉。#92: 「このテストでしか確認できない」性質を壊すと、赤くなった 4 件のうち 3 件は既存テストだった)

## 契約と写像を固定するテスト

- **散文の契約を条項に分解**: JSDoc・コメント・AC・コミットメッセージが「必ず〜」「A または B のとき〜」「常に」「一切〜ない」「この経路には来ない」と宣言していたら、1 文を接続詞で条項に割り、条項ごとにテストがあるかを突き合わせる。コードの分岐に現れない約束(順序・付随情報・2 ファイル間の取り決め)は、分岐から作る表に載らない。各主張が偽になる最小の変異を入れて全緑なら、その文は実装の性質ではなく作文なので、テストを足すか、断定を落とさせる。`または` で列挙された側は、片方しかテストされていないことが多い。是正タスクが自分の新しい JSDoc で同じ穴を作っていないかも見る。(#62: 「`ok` が false または欠落」の欠落側に正の対照が無く、弱める変異が全緑。#70: 「払戻が取込済みでも常に除外する」と書かれたが、条件を足す変異が全緑)
- **生産者と消費者**: センチネル文字列・argv の順序・終了コードの意味・環境変数のように、一方が出力し他方が解釈する取り決めは、どちらの単体テストにも現れない。両端をつなぐテストを要求する。ゲート・バリデーション・CI 関門は、`status === "block"` を assert して満足せず、守る対象の破綻を実際に注入し、返る message に原因が載るかを目で見る。診断を捨てる検査は、fail-closed でも目的を達していない。「壊れても CI で落ちるから問題ない」は、落ちることと、落ちたときに診断が残ることを混同している。(#62: ABI 不一致を注入すると、原因を含むセンチネルが終了コード分岐に捨てられ、ログには「exit code: 1」だけが残った)
- **写像の検証**: 入力のフィールドを読んで出力のフィールドへ書く変換(View 型への写し取り・DTO 変換・DB の行の組み立て)は、同じ型の隣接フィールドの取り違えを型検査が検出しない。値を assert したことを、写像を検証したことと等置しない。(1) 入力フィールド × 出力フィールドの対応表を作る(`grep -o 'row\.[a-zA-Z]*'` 等で機械抽出し、入力型の全フィールドと突き合わせる)。(2) 各行を入れ替え変異で潰す。フィクスチャの値は、隣接フィールドどうしで相異なるようにする(同値の対や、常に null の列は、入れ替えも `null` への潰しも検出されない。全列を `toEqual` で固定しても同じ)。(3) 入力側が複数の異なる値をとるテストがあるか見る。判定は、当該出力を定数に置き換えて全テストを流し、全緑なら未検証である。SQL の位置パラメータ(`INSERT ... VALUES (?, ?, ...)` と `stmt.run(a, b, ...)`)は最優先で疑い、列リストと実引数の並びを機械的に突き合わせる。実装から import した定数どうしの比較(`toEqual([SOME_NOTE])`)は、同一のバインディングなので定数の中身が変わっても緑になる。外部に見える文字列は、ハードコードしたリテラルとの `toBe` を併置させる。app が組み立て core が保存する二層は、層ごとに表を作り、app の作った値が DB まで届く結合テストの有無を確認する。(D-2c 第2段: `adjustedProb` を `prior` に差し替える変異など 3 種が全緑で残った。#59: `unavailable_reason` を `null` に潰す変異が全緑。AC の「全 20 列を `toEqual`」は守られていたが、値が列を識別していなかった)

## 回帰テストの継承と受け入れ条件の照合

- **回帰テストの継承**: 契約変更で既存テストファイルが大きく書き換えられると、無関係な回帰テストが巻き添えで消える。テスト名の差分は、改称でほぼ全件変わるとノイズだらけになる。旧版を `git show <旧コミット>:<パス>` で取得し、テスト名ではなく「何を保証していたか」を列挙して、旧の各項目に「新のどのテストが継承したか / 意図的に削除した(理由付き)」の対応表を作り、未分類をゼロにする。「同等のテストがある」という主張は、同じ強度か(既定値しか見ていない等の弱体化がないか)を自分で読む。AC が「元の無条件 expect をすべて引き継ぐ(…)」と括弧内で列挙しているときは、項目に番号を振り、`expect(` 行を全部抜き出して、番号ごとに該当行を指す。指せなければ指摘する(「実測したら成立しているから実質同じ」は理由にならない)。コピー元から複製した双子のテストは、`diff` でコピー時に落ちた行を探す。(C-2: 名前の diff では 1 件の消失を見落とした。#81: 複製した PL 版から「丸め後も 2 頭とも正」の検査が落ちており、code-reviewer は 3 回のレビューで検出しなかった)
- **名前ではなく本体**: `describe("受け入れ条件N: ...")` の見出しやテスト名は、その条件が検証されている証拠にならない。名乗る主張と、本体の入力・アサーションが一致するかを 1 件ずつ突き合わせる。条件の主語と、比較が成立する前提(「キャップ拘束時」を名乗るなら `capApplied===true` が成立するか)を実測する。「A しても B が壊れないこと」の条件は、後件(壊れない側=下流)を実際に走らせるテストがあるかを確認する(A を作る関数のテストは B の検証ではない)。(C-2: キャップが一度も拘束しない設定で別の性質を検証するテストが、AC7 を名乗り、5 周のレビューを通過した。#40: フィルタ関数のテストだけがあり、下流の `computeFieldPriors` を通すテストが無かった)

## 数と列挙の照合

- **数えられる断定**: JSDoc・コメント・報告・コミットメッセージの「次の 2 箇所」「3 パーサすべて」「全 N 列」は、レビュー時に自分で数えて照合する(`grep -rln 'from "./xxx.js"' src | wc -l` 等)。数を間違えた散文はテストを落とさないので、変異注入では検出できない。次の点も確かめる。
  - 数どうしの一致: 同じ集合を差分内の複数箇所が数えているなら、数どうしを突き合わせる。申告された件数は数え直し、訂正報告の数値も実測してから書く。
  - 自己参照する数: 差分が新しく書いた数は、差分適用後の状態で数える。「テストは N 本」は、その差分が N+1 本目を足すと外れるので、HEAD と base(`git show <base>:<パス> | grep -c`)の両方で数える。
  - 単位と定義域: 「N 経路」が定義の数か呼び出し箇所の数かを確定させ、網羅の主張は呼び出し箇所の単位で数え直す(`grep -c` は行数、`grep -o | wc -l` は出現数)。定義域は関数名でなく、その概念の値が代入されるフィールドで走査する(名前の走査は、別名の汎用ヘルパで作る経路を見逃す)。誤りと判明した数詞は、追加行から grep して再発を潰す。
  - 網羅表現: 数詞の無い網羅・唯一性の断定(`すべて`/`いずれも`/`のみ`/`一切`/`常に`)と、範囲表現 `N〜M` も走査する。`docs/` も対象に含める。
  - 埋め込みコマンド: 「`grep ... ` で確認可能」と書かれていたら、そのまま実行して件数が一致するかを見る(パターンは実装の表現に依存して腐る)。一文が数を 2 つ以上断定するなら、結論を支える側をコマンドが再現するか、コマンド内の定数(バイト窓幅・`head -N`)を変えて出力が動かないかを見る。
  - (#34: レビュー 4 巡が数え直しの是正に費やされ、LGTM 後も「4 パーサ」が残った。実際は 3 で、grep 1 本で反証できた。#74: 「総出現数13」と書いた文自身が 14 個目だった。#73: 「5 経路」は定義の数で、呼び出し箇所は 12 あり、3 箇所が無検査だった)

## 数値の再現性

- **一次データと再現手段**: 差分に現れるすべての数値主張(`docs/`・JSDoc・コメント・テスト名)について、repo 内のどのファイル・コマンドで再現できるかを答えさせる。答えられないものは、値が正しくても指摘する。追加行は `git diff <base> HEAD | grep -E '^\+' | grep -E '[0-9]+\s*(ms|秒|件|%|倍)|中央値|平均|p95|実測'` で機械的に洗う。
  - 実測調査タスクは、数値を導いた応答・HTML・JSON がコミットされているかを見る。「取得したが保存しなかった応答」に基づく主張、導出値(算術的帰結)と観測値の混同、ゼロコストで得られる証拠の取りこぼしを疑う。(D-1: 取得した `result.html` に「複勝の払戻点数が 2 点」の直接証拠があったのに、記録されていなかった)
  - 差分の外にも当たる。AC・JSDoc が、レビューの外で先にコミットされた数値(`docs/issue-order.md`・Issue 本文からの転記)に依拠していたら、既存行でも再現手段を答えさせる。修正は、数値を落として式・手順を書くか、再現スクリプトをコミットする。(#81: 使い捨てスクリプトで測った数値が、レビューを経ず `docs/issue-order.md` に入った)
  - 「検証手段のない数値を測定値の口調で書く」問題は、繰り返し再発している(必要総資金の倍率・連続最適比率・出馬表の頭数の数え方・地方 3 連複の軸馬別取得・JSDoc 内の性能ベンチマークなど)。
- **性能ベンチ値と無作為入力の比率**: ms・スループット・p95 などは、コミット済みのスクリプトが無ければ指摘する。再現手段を用意しない代替は、測定値の口調をやめて根拠の性質を書くこと(「最大 816 組という有界な入力に対し、追加コストは無視できる」)。外部データには丁寧でも、同じ差分の自前の測定値だけ再現手段が無いことがある。乱数で生成した入力の「発生率 X.XX%」は標本統計なので、`N` が併記されているか、`sd ≈ sqrt(N·p·(1−p))` より細かい桁で優劣を語っていないかを見て、疑わしければ種だけ変えて再実行する。表全体の傾向が頑健でも、各セルの下位桁に意味があるとは限らない。(D-2b-A: JSDoc が ms 値を再現手段なしに載せていた。#80: N=3200・p≈0.03 の表の値が、種を変えるだけで 3.09%→2.72% と動いた)
- **他所を名指しする主張**: 「`xxx.test.ts` の AC17〈5 件〉が固定している」「`Foo.tsx:625` が `useMemo` なし」のような件数・行番号・存在の主張は、再現手段が明白なために検算が省かれる。実際に `grep -c` や `sed -n` で確認し、行番号・件数による参照は、名前による参照へ置き換えさせる。(#31: 「5 件」は実際は 6 件だった。「`useMemo` なし」は、memo 化が別の仕組みで実装済みだった)

## 散文が述べる理由・到達条件・帰属

- **理由の個別反証**: 「〜であるため、〜になる」は、結論が正しいことを確かめても理由が正しい保証にならない。追加行から「〜のため」「いずれも」「常に」「〜だけ」を洗い、その主張が「無い」と述べる性質を持つ実例を、同じファイル・差分から探す。1 件でも見つかれば、結論が変わらなくても理由を直させる。「余裕がある」の主張は、実際の余裕を測って値を併記させる(量指定子の多い正規表現は、リテラルを除いた隙間ごとに測り、注入で分岐点を確かめる)。数値の出所を名指しする主張(「旧版の N% は〜という方法で測ったもの」)は、走査語に「で計測した」「母集団が異なる」「方法が違う」「旧版」を加え、名指しされた方法を実行して、その数値が出るかを見る。「訂正済み」のラベルは、訂正の理由が正しい保証にならない。文面の出所がメインの推奨や実装者の報告でも、検証を免除しない。(#44-D-1: 注記の「いずれも改行を挟まない」は、5 パターン中 3 つで偽だった。この理由は boss の推奨文面の採用で、差し戻しで boss が示した「余裕が 6 文字」も誤りだった。#80: 旧値「14.5%」を「同じ生成方法で計測したもの」と説明したが、実行すると 1.0%/1.5% だった)
- **到達条件**: 「`coef` が非有限であるためにこの分岐に入る」「〜のときに限り」のように、分岐に入る入力を特徴づける記述は、(i) 条件を満たすのに入らない入力と、(ii) 条件を満たさないのに入る入力を、両方向とも `node -e` 等で実行する。浮動小数では、有限入力から非有限値が出る(`(1e308-1)*1e10`)、非有限入力から有限値が出る(`Math.max(1.0, -Infinity)`)、`0 × Infinity → NaN` があり、「非有限が混じったときだけ壊れる」という直観はいずれも偽になる。もう一方のパラメータを自由変数のまま残した断定は全称命題として読まれるので、境界値(`MIN_VALID_ODDS`・`0`・`±Infinity`・`NaN`)を代入して実行し、全称で読まれたくない記述は値を束縛して書かせる。内点で 1 つ試して真だったことは反証にならない。利用者に出る文言が原因を選言で列挙するなら、各要素が到達可能かを確かめる。`実測: X → Y` と掲げた反例は、同じ入力を通すテストがあるか確認する(射程は、対象コードの分岐を特徴づける実測。言語組込みの挙動を引くだけの実測は、自コードの不変条件として固定できるかを見る)。AC が「偽になった原文を削除する」形のときは、置換後の文を独立に検証する。「旧版は〜だった」という過去形の断定は、`git show <親コミット>:<パス>` で旧実装を読んで照合する(変異注入では検出できない)。(#88: JSDoc が「非有限であるために」と特徴づけたが、同じコミットのテストが `coef=-Infinity` の別の結果を固定し、有限の値でも到達した。「旧版は 3 状況を null へ統合していた」は、旧実装が生の NaN を返していた〈それが直した欠陥そのもの〉と食い違った)
- **2 つの実測値が食い違うとき**: 「集約規則の違い」「前提が違う」のような、検算されていない機序を、尤もらしさで受理しない。両手法を同じ最小単位(ファイル・レース・行)へ分解した対応表で、一致する単位と食い違う単位を先に確定し(合計だけを比較しない)、食い違う単位の戻り値を根拠に書く。どれか 1 つが単なるバグである可能性を先に潰し(`node -e` 1 行で済むことが多い)、数は丸めずに単位を明示して併記する。(#74: オッズ個数が 464/440/474 と 3 通り出て、「集約するため」と説明されたが、分解すると 12 ファイル中 10 は一致し、474 は桁区切りカンマを処理していない単なるバグだった。指摘を直すコミットが新しい誤りを持ち込むことが 3 回続いた)
- **帰属**: 「boss が〈コミット済みの〉スクリプトで実測した」「メインの実測」「実証済み」のような記述は、帰属先が実際に測ったか、その成果物が当時存在したかを `git log --follow -- <パス>` と `git log -S '<文字列>'` で確かめ、時系列が主張と整合するかを見る。事実の訂正と帰属の訂正は別で、前者だけ直すと「していない測定を根拠として名前が残る」(`docs/lessons-learned.md` 2026-08-22 の項と同型)。
- **直後数行**: 最も見落とされるのは、編集した記述と同じ JSDoc ブロックの 2〜5 行下である。各ハンクの変更行の直後 5 行を読み、変更した主張の古い版や、その理由が残っていないかを見る。特に「〜のため到達しない」という到達不能性の根拠は、判定基準を変えた差分では機序ごと古くなる。(#74: 規則 U の JSDoc を書き換えた直下に変更前の機序が残り、一部の経路で偽だった)

## 旧い記述の全数走査

差分が事実や振る舞いを変えたとき、変更した本人は書き換えた箇所しか見ていない。変更した事実のキーワードで repo 全体を走査し、偽になった記述を探す。新しいリテラルを grep して「全箇所で一致した」と確かめる方法は、新リテラルを持たない更新漏れの文書を発見できない。

- **旧語での走査**: 既定の振る舞い(規約・CI・運用フロー)を変える差分、または記述の誤りを訂正する差分は、変更前の振る舞いを表す旧語(「push ごとに」「毎回」「常に」+ 対象名)や、訂正した主張に含まれる固有名詞・数値・エラー文言で、repo 全体を `git grep` し、ヒットを 1 件ずつ新仕様と突き合わせる。訂正した文そのままでは、言い換えられた要約が一致しない。次を探索範囲に含める。
  - 差分に現れない場所: `.github/workflows/*.yml` の冒頭コメント、`.claude/agents/*.md`、`docs/handover-*.md`。変更したファイル自身のヘッダや冒頭 JSDoc・見出し・表の要約行は、旧い記述が頻繁に残る。
  - `docs/` だけでなく `packages/*/src/**` の JSDoc・コメントと、`packages/*/test/**` のコメント本文。走査語は活用形を網羅する(「切り替える」「切り替えた」「切替済み」「〜のまま」「〜だった」)。同じファイルの別の場所を是正している差分では、全文を読む。
  - ヒットが「歴史的記録」か「次に読む人への現在形の指示」かを判定し、現在形の指示なら指摘する。不変条件テストで旧文言を見張っているなら、その検査の対象ファイル一覧が、この走査の結果と一致するかも確認する。訂正コミットが再発防止策を書いていても免除しない。
  - (#81: 既定モデルの切替で、current-spec と JSDoc 1 つは是正されたが、同一ファイルの見出し「## 既定は変えない」ほか「〜のまま」の記述が残ったまま LGTM に至った。#62: 再発防止策を書いたコミットの中で 3 回目の誤りが起き、4 回目が残った)
- **型のメンバー集合を増やす差分**: ユニオン・`Record` のキー・`KNOWN_*` 配列にメンバーが増えると、「A/B/C のいずれか」と言い切る既存の JSDoc・コメント・カバレッジ表は、その瞬間に偽になる。テストが赤くならないので、レビューでしか見つからない。差分が触った型のメンバー名(`"place/wide/trio"` のような連結表記・`・` 区切りも)で repo 全体を grep し、各ヒットが何のドメイン(型のメンバー集合 / DB 由来の開いた文字列 / 設定トグル / 過去の決定の引用)を語るかを分類した表を報告に添付して、型のメンバー集合を語るものは更新を要求する。同一ファイル冒頭のカバレッジ表とインライン JSDoc を含める。「次の Issue で触るから」は理由にならない。ファイルを読むのではなく、主張に使われている語で grep する。(#91: 新しい値を足した差分で、冒頭のカバレッジ表と「3 値」の JSDoc が残り、再レビューも 1 件しか報告しなかった)

## 永続化スキーマの変更

列を足した migration は、空の DB に全部適用すれば必ず緑になる。テストが新規の DB だけで書かれていると、適用の順序・旧い Worker との共存・新しい Worker が先に出た場合の被害が、全緑のまま通る。本番の D1 は CI にもリポジトリにも存在せず、自動で守られるのは `scripts/test/cloud-d1-schema.test.ts` の宣言と、`deploy-cloud.yml` の check ジョブがローカルの D1 に migration を適用することまでである。

- **先例の形**: `cloud/migrations/` に新しいファイルが現れたら、`cloud-d1-schema.test.ts` が既存の migration に対して固定している形(一覧への登録、D1 専用の列の宣言、直前までに列が無いこと・索引が増えないこと・SQL が `ADD COLUMN` だけであることを 1 件ずつ固定するテスト)を数え、新しい migration だけがその慣行から外れていないかを見る。外れていれば報告する。(exe の SQLite 時代に、列の追加で旧 DB を開くテストが 1 本も追加されなかった事例〈#100〉と同じ教訓で、慣行の数え方で逸脱を見つける)
- **migration の性質と適用順序**: 報告の前に、自分で確かめる。(a) 追加のみか(`DROP`・`RENAME`・型変更で既存を壊さない。`UPDATE` があれば本番の件数で通るか)。(b) 旧い Worker と共存するか(直前の Worker の INSERT・SELECT が新スキーマで通るか。新しい索引・CHECK・UNIQUE が旧 Worker の INSERT を弾かないか)。(c) 直前までの migration を空の DB に適用して既存行を 1 件入れ、新しい migration を適用して行が残ること。(d) `deploy-cloud.yml` が `wrangler d1 migrations apply` を `wrangler deploy` より前に置いているか。(e) 新しい列を使う Worker があるなら、`cloud/src/d1-health.ts` の `D1_HEALTH_SQL` がその列を指しているか(migration の反映前に新しい Worker が出た状態に気づく唯一の経路)。(f) 新しい Worker が migration より先に動いたら何が落ちるか(読み出しだけか、保存まで壊れるか)を列挙する。「動くこと」と「テストがあること」を分けて報告する。
- **UPSERT の `DO UPDATE SET`**: 新列を足したときは、その列を渡さない呼び出し元(テストヘルパ経由を含む)がいないかを全数確認する。いれば、再保存が既存値を静かに NULL で上書きする。

## 計測スクリプト・ベンチの入力生成

「本番相当」を名乗るベンチ・計測スクリプトは、入力を作る各段を production の実コードと 1 段ずつ対応付けて報告させる。

- **確率 0**: 本番で到達する値が、その生成器では確率 0 になっていないか。連続一様分布から引くと、クリップ境界(`max(0, x)`/`min(1, x)`)にちょうど一致する値は二度と出ない。本番がその境界値を生成するなら、生成器は最も難しい入力クラスを構造的に除外している。
- **分布の中心・裾と判断材料**: 「〜付近を中心に」と書いてあるなら、平均を計算して確かめる。その数値が他タスクの判断材料に指定されている場合は、何を測り何を測っていないかを数値とともに明記させる。

## CRLF と LF

CI は `ubuntu-latest` だけで走る(Issue #248 で Windows ランナーを廃止)。それでも、利用者の checkout は CRLF になりうる。差分にリポジトリ内のファイルを読むテストがあるなら、読み込み直後に改行を LF へ正規化しているかを確かめる。(過去に、`\n` を要求する正規表現が、ローカルの LF で緑、CRLF の環境で失敗した)
