# レビューの観点集

`.claude/agents/code-reviewer.md` から走査の観点を移した文書である(Issue #606)。観点は、過去のレビューですり抜けた欠陥から積み上げた。レビュー担当は、差分の種類に合う節だけを読む。
Issue #609 で、重複する観点をまとめ、事例の経緯を縮めた。書き直す前の観点の一覧と対応は `docs/investigations/review-checklist-inventory.md` にある。

## この文書の使い方

- 観点は「見つけ方」であって「止める基準」ではない。見つけたら、CLAUDE.md「★ブロッキングの基準」の 3 区分で【要修正】か【記録】かを決める。
  - 【要修正】にしてよいのは、(1) 利用者から見える誤り、(2) production から到達できる契約違反、(3) クラッシュ・データ破損、の 3 つだけである。
  - 散文(JSDoc・コメント・テスト名)の不正確さ、到達できない経路のテスト不足、数値として無害な変異の生存、命名や好みは【記録】である。
- 本文の「指摘する」は、観点に当てはまったという意味である。区分は上の基準で決める。
- 「変異注入」は、守りたい挙動を壊す変更を実装に入れて `pnpm test` を流し、赤くなるかを見ることである。「全緑」は、その変異を入れても全テストが緑のままという意味である。
- 事例の `boss` は、2026-09-24 に廃止した旧役割である(着手前ゲートとメタレビューは、いまメインセッションが担う)。「exe」「SQLite」の事例も当時の記録で、exe のコードは Issue #285 で削除した。事例は経緯の記録なのでそのまま残す。

## 差分の種類ごとの読む節

| 差分の種類 | 読む節 |

| リポジトリ内のファイルを読むテスト | CRLF と LF |

## 基本の観点

- **仕様適合**: `docs/current-spec.md`(実装済みの現状仕様。`keiba-ev-tool-spec.md` は当初計画の記録)の該当箇所と突き合わせ、乖離・解釈違いがないか。
- **TDDの形骸化**: テストが実装の写しになっていないか。境界値(サンプル不足時の補正なし、休み明けの分類境界等)があるか。失敗しうる意味のあるアサーションか。
- **正確性**: 計算の誤り、off-by-one、null/undefined の処理、日付・レース間隔の計算。
- **スクレイパーの堅牢性**: セレクタの集約、取得失敗時のフォールバック、レート制限の遵守。
- **規約**: コメント・ドキュメント・テスト名が日本語か。
- **保守性**: 過度な複雑さ、重複、責務の混在。

## ユーザー向け説明文と実出力

- **1対1で照合する**: UI の注記・プレビュー・ヘルプなど「実際に何が起きるか」を説明する文言は、対応する実出力(プロンプト文面・生成物)の全条件分岐を自分で洗い出し、矛盾がないか照合する。「このまま送られる」「このデータに置き換わる」の断定は、条件付きの要素(天候・馬場の分岐、未保存入力と保存済み値の差、欠損時の表記)を見落としやすい。実出力は tsx/vite-node 等で実際に生成して突き合わせる。
- **原因を名指しする文言**(「〜の制約により」「〜のため」)は、出る全経路で原因が真かを、条件が成立する入力を複数通り走らせて実測する。フラグの計算の正しさと、添えた原因説明の正しさは別の検証である。core が原因を書いていないフラグに renderer が原因を足していないかを疑う。文言のテストが出現順・件数だけで、内容が真であることを検証していないなら指摘する。(C-2: 上限が効かない経路〈丸め・最低額〉でも「1レース上限の制約により」と出た)

## 新経路・並行する系での継承

- **新経路の表示要素**: 同じ画面領域を描く別経路を横に足す変更(券種・モードの追加)では、何も削除していないのに、既存経路の注記・警告だけが新経路に無いことがある。既存経路が描画する要素(テーブル・合計行・条件付き注記・固定注記)を全数列挙し、新経路の同じ状態に対応する要素があるかの表を作る。「無い」セルは、出さない理由が JSDoc にあるかを見る。共通ヘルパー(`buildXxxNotices` 等)を使わず自前で組み立て直している箇所を疑い、型の非互換が理由なら、元データが呼び出し側に残っていないかを確認する。(D-2c 第4段: 混在経路だけ確率合計警告が無く、`docs/current-spec.md` は「警告を出す」と書いたままだった)
- **並行する 2 系の欠損値**: 同じ結果テーブルを別の規則で集計する系を足す差分は、`null`・未取得・対象外の扱いが抜けやすい。入力の各フィールドの欠損しうる値を列挙し、「既存系 / 新系 / 違いが書かれているか」の 3 列の表を作る。違いが実装にしか無ければ指摘する。直前のタスクがその欠損値を扱っていたら最優先で見る。(#71: 新系が取消・除外馬を不的中として分母に積み、回収率を下振れさせた。既存系は集計対象外と明記していた)

## 欠陥クラスの水平展開

バグを 1 件見つけたら、同じ失敗モードが他の入力・フィールドに無いかを全数で洗い、最初のレビューで一度に報告する。1 箇所だけ指摘すると、同種の残りが次の周で必ず出る。(C-1: 「未判定を判定結果として報告する」欠陥と「設定値の無防御による NaN の漏れ」が、3 周連続で別フィールドから再発した)

- **数値の異常値注入**: 入力の防御漏れを見つけたら、その関数の設定オブジェクト/引数の全数値フィールドに `NaN`/`±Infinity`/負値/0/範囲外/非整数を注入し、出力が有限で契約(上限・単位・不変条件)を守るかを表で確かめる。
- **配列・Map の要素**: 数値フィールドには、配列・Map で渡される要素の中の数値も含む。要素 1 件の `NaN` が、無関係な健全な要素の計算まで壊すことがある。構造の検証(並び・重複・空)があるのに数値の検証が無い非対称、同一関数内で防御した値としなかった値が混在することは、それ自体を指摘する。(D-2a: 候補の `odds` の `NaN` で、無関係な健全候補の配分まで消え、レース全体が誤った見送り理由になった)
- **説明系フィールド**: 理由文言・分類フラグ・診断値の誤りを 1 件見つけたら、同じ結果オブジェクトの他の説明系フィールドすべてについて、その値の算出経路を実際に通ったかを確認する。通っていない経路の結果を報告している値は同じバグである。
- **JSDoc の状態対応表**: 「`undefined` なら未取得」「`{}` なら発売なし」のように状態と原因を 1 対 1 に対応づける記述は、その状態を作る全経路を実装から洗い、本当に 1 対 1 かを確認する。違うなら、原因を判別するフィールドを明記させる。(D-2c 第1段: `AnalysisResult.wideCombo` の JSDoc が「`{}` = 発売なし」としたが、取得失敗〈`state==="failed"`〉でも `{}` になる。同じ差分の別の JSDoc の誤りを直させたあと、同種の記述を走査せずに LGTM を出した)
- **列挙値・文言定数のドメイン**: `switch`/`Record`/`includes` で分岐する対象は、(a) 取りうる値の全集合(型定義・`KNOWN_*`・判別共用体)の表を作り、(b) 各値について戻り値が値として固定されたテストが差分にあるかを埋め、(c) 空白セルに変異を注入して全緑かを実行する。未知値へのフォールバック分岐も含める(最も試されにくい)。(#55: 同じ欠陥クラスが 3 ラウンドに分かれて出た。`"unknown"` はテスト入力に一度も使われていなかった)
- **多分岐の最終 else**: `if (A) … if (B) … else return C` は、A でも B でもない入力に C を断定する。壊れた DB 行や旧データで、利用者に偽の断定を出す。最終分岐が判定結果(理由・原因・ラベル)を返す箇所(`if/else if/else`・`??`・`? :`)で、落ちる入力が 1 種類しか無いかを型と実装から数える。2 種類以上なら指摘し、「判定できない」を述べる別の出力を用意させる。同じモジュールの他の想定外入力に専用フォールバックがあるのにここだけ断定している非対称は、強い兆候である。(#55: 総資金も上限も 0 より大きい記録に「1レースの上限が0円のため…」と返した)

## テストの空振り

- **条件分岐内のアサーション**: `if (...) { expect(...) }` は、前提が成立するかを実行して確かめる。差分のテストから条件分岐付きアサーションを grep で洗い、入力を tsx 等で実行して分岐が真になることを実測値で示す。修正は、前提を無条件 `expect` で分岐の前に固定すること。(C-1: `if (betCount >= 2)` の前提が実測 `betCount = 1` で常に偽になり、テスト本体が一度も実行されなかった)
- **分岐が無くても空振りする**: 不等式・差のアサーションは、入力によっては左辺が常に 0 で自明に成立する。テスト名が「差」「剰余」「上界」を名乗るなら、その差が 0 でないことを無条件 `expect` で先に固定する。実測値が境界から桁違いに離れているのは「余裕」ではなく、現象が起きていない証拠であることが多い。「成立したか」ではなく「検証対象の現象が発生したか」を問う。(C-2: 剰余の再配分のテストが退化配分になり、丸めが一度も起きず、実装を変えても通る状態が 2 周見逃された)
- **退化入力**: 1 頭に全額集中・`betCount===1`・`Σx*` が 1.0 や 0 に張り付く配分は、貪欲最適化で頻出する。多点配分を前提とするテストは、`betCount` を無条件 `expect` で固定する。
- **禁止事項の不在**: `.toBe(false)`/`not.toContain`/`not.toMatch` のように何かが無いことを主張するテストは、検出器(正規表現・キーワード)側を壊すだけで永久に緑になる。検査される側にだけ変異を入れても、検出器が生きている証拠にならない。検出器が真を返す入力を固定したテスト(正の対照)があるかを探し、無ければ、過去に実際に問題だった文字列(`git show <事故コミット>:<パス>`)を `toBe(true)` で固定させる。検出器自体に変異を入れて全緑なら、その不変条件は実質存在しない。「対象文字列が無いことをまず確認する」というコメントは `toBe(false)` の言い換えにすぎない。(#43)

## テストの検出力(変異注入)

検出力は、読んで論証するのではなく、変異を注入して自分で `pnpm test` を流して確かめる。実装者の「壊して失敗を確認した」は、どの粒度で壊したかを聞き、守りたい退行と一致しなければ注入し直す。

- **ソース走査テスト**: 識別子・文字列がソースに現れることの検査(`toContain("display.foo")`)は「書かれている」であって「使われる」ではない。`push` の行だけを消しても `if` 行に同じ識別子が残り、通る。振る舞いテストの代替として認めず、組み立てロジックを純関数に切り出して戻り値を直接 assert する形を求める。変異は最小の単位で入れる(文を 1 本消す・`push` だけ消す)。ブロックごと/`import` ごとの粗い変異で落ちても、細かい変異で落ちる証拠にならない。(D-2c 第4段: `notices.push(...)` の 1 行削除が素通りした。実装者の変異は `if` ブロックごとだった)
- **fail-open**: 条件を置き換える変異(`A`→`B`)だけでなく、選言で広げる変異(`A`→`A || B`)も試す。`B` が真の状態で「その出力が現れないこと」を主張するテストが無ければ素通りする。空セルを「他のセルで間接的に守られている」という論証で埋めない。各テストが、操作していない側のフィールドの不在・既定値を assert しているかも見る。(D-2c 第1段: 3 フィールドの有無の表の残り 2 セルを論証で埋めたが、`|| wideCombo !== undefined` を足す変異が全緑だった)
- **対になる 2 状態の両方向**: 「キーあり値 `null`」と「キーごと不在」のように 2 状態を区別する契約は、片側だけのテストでは、もう一方へ退化させる変更(`null` を落とす・不在を `null` で埋める・空配列を `undefined` に丸める)を検出できない。それぞれの状態を作る入力のテストを探し、無い側を潰して全緑かを実行する。対はデータの形に限らず、同一関数の分岐と条件式の真偽も同じである。「全分岐 × 新しく足した情報の有無」の表を作り、空セルを 1 つずつ潰す。1 種類の破壊を示したことを、変更全体が固定された証拠にしない。(#33: `missing` と `unfetched` のうち `unfetched` 側だけがテストされていた)
- **演算子の極性**: 設定ファイル・ワークフロー・条件式を文字列や構造で検査するテストは、`toContain` による要素の存在確認では、演算子の反転(`!=`→`==`、`>`→`>=`、`&&`→`||`、否定の有無)を検出できない。破壊で検証したと報告されたら、極性反転を含むかを見る。(CI のスキップ通知の条件 `!= 'true'` を `== 'true'` に反転しても 6 件全緑だった)
- **新設分岐が既存ロジックの複製**: 新しい経路を足す差分は、既存の判定式を書き写した第 2 の実装を生みやすい。赤くなるのは既存側の 1 本だけで、複製側は無防備になる。(a) 新設分岐の述語・集計式と同じ式が既存経路にも無いかを grep し(`every`/`some`/`includes`/`filter`)、(b) 複製側だけを変異させて該当パッケージ全体の `pnpm test` を流し、(c) 全緑なら指摘する。「新設分岐の出力を検査するテストがある」は根拠にならない。`toBeGreaterThan(0)`・`Number.isFinite(x)` のような述語検査は検出力の要件を満たさず、値そのもの、または既存経路の戻り値との突き合わせを求める。(#92: 的中判定の `every` を複製した新経路で、`every`→`some` に変異しても全緑のまま、ワイドの的中確率が 13 倍に化けた)
- **対をなす関数の分岐表**: 複製は、値による場合分け(`=== 0`/`=== Infinity`)としても現れ、短い式の grep にかからない。`buildX` ↔ `buildOrderedX` のような対の関数を新設したら、(a) 新設関数の全 `if`/`else if`/early-return を列挙し、(b) 各分岐を通す入力を持つテストが実在するかを grep で確かめ(分岐を通さないフィクスチャばかりなら 0 本と同じ)、(c) 空白セルに変異を注入する。既存側に専用の集合(`zeroSet`・未知値・空)があるのに、新設側のフィクスチャにその値が 1 件も出ない形は強い兆候である。分岐を単独で数えず「分岐軸 × その分岐が読む他の分類結果」の 2 次元の表にし(3 軸以上へは広げない)、分岐を通すフィクスチャが他の集合について退化(常に空/常に全件)していないかも見る。(#92: θ 分類を複製した新設関数で、`placeProb: 0` を含むフィクスチャが 1 件も無く、θ=0 の扱いを変える変異が全緑。p=0 を含むレースは実データで支配的だった)
- **共通関数に引数を通した差分**: 同じ共通関数が 2 つ以上の経路(集計ループとレース単位ブレークダウン等)から呼ばれていると、片方だけテストが厚く、もう一方は引数の配線だけでテストが無いことがある。呼び出し元ごとに、その引数を定数(`false`/`null`/既定値)へ潰す変異を注入する。両経路の合算一致テストは、新しい引数が分岐を変える組合せをフィクスチャが踏んでいなければ値が動かず、この穴を塞がない。(#70: `buildRaceBreakdown` 側の `racePayoutAvailable` を `false` に潰す変異が全緑)
- **配り先**: 1 つの束縛(フラグ・判別結果・共通関数の戻りフィールド)を複数の消費点へ配る差分は、出現箇所を grep で列挙して確かめても、検出力の証明にならない。(a) 読み手を全数列挙し(AC に無いものも)、(b) 読み手ごとに、その 1 箇所だけを別の値へ差し替える変異を注入し、(c) 全緑の読み手が 1 つでもあれば指摘する。「読み手の 1 つが固定されていれば足りる」は、全読み手を一斉に壊す変異にしか効かない。あわせて読み手が 0 個のフィールドを探す。core で計算して View 型まで配線したのに UI が読まない値は、変異を当てる相手が無いだけでなく、説明責任が利用者に届いていない。出力フィールドは最終的な消費者を追い、0 なら指摘する。(#70: 読み手 4 箇所のうち 2 箇所が全緑。#71: 分母から落とした買い目の点数が画面に現れず、「ワイド0点」の意味を区別できなかった)
- **既定値の切替**: 検出力の欠落は `not.toBe(旧既定)` という書き方に限らない。(i) 新既定と食い違わなくなる、(ii) 肯定形 `toBe(リテラル)` が偶然新既定と一致する、(iii) その値を検査するテストが無い。grep で書き方を探すと (ii)(iii) は落ちる。(a) 切り替えた値を読み出している production の全箇所を列挙する(切替点でなく読み出し点。テスト側も全パッケージ横断で)。(b) 各読み出し点で、引数を無視して新既定/旧既定をハードコードする変異を注入してフルスイートを流す。(c) 赤が 0 本なら指摘する。「同型の欠陥は他に無い」と結論する前に、(a) の列挙が網羅的であることを示す。(#81/#86: 全数走査 0 件を根拠に「同型は無い」と報告されたが、`allocateGeneralBets` の `modelId`/`modelApproximate` を現在の既定へハードコードする変異が全緑だった。boss の「検査するテストが無い」も、走査を 1 ファイルに限った誤りだった)
- **旧既定との比較**: 「既定と異なることを確認する」型のアサーションは、既定が変わった瞬間に空振りする。`not.toBe(X)`/`not.toEqual(X)` の `X` が旧既定を指していないかを見て、指していれば、新既定を代入しても落ちるかを確かめる。コメントを直すだけでは検出力は戻らない。(#81: スタブの `approximate:false` が新既定 PL と一致し、新既定をハードコードする変異を検出しなかった)
- **先送りの根拠と検出力の断定**: 陳腐化しかけた記述を次の Issue へ送る判断は正当だが、根拠が「将来 ◯◯ を触れば自動的に赤くなる」なら、それは検証可能な断定である。将来の変更を今この場で注入し、赤になるファイルと緑のままのファイルを 1 つずつ列挙する。反対向きの断定(「このテストでしか検出できない」「唯一」「原理的に検出不能」)も、他のテストが赤くならないことを変異で確かめるまで受理しない(`しか確認できない`/`しか検出できない`/`原理的に`/`唯一`/`のみが検出` で grep)。是正すべきは断定の方で、テストは消させない。(#91: 注入した変異に対し `verify-format.test.ts` は全緑〈`verify.ts` を通らない〉。#92: 「このテストでしか確認できない」性質を壊すと、赤くなった 4 件のうち 3 件は既存テストだった)

## 契約と写像を固定するテスト

- **散文の契約を条項に分解**: JSDoc・コメント・AC・コミットメッセージが「必ず〜」「A または B のとき〜」「いずれの場合も〜」と宣言していたら、1 文を接続詞で条項に割り、条項ごとにテストがあるかを突き合わせる。コードの分岐に現れない約束(順序・付随情報・2 ファイル間の取り決め)は、分岐から作る表に載らない。各主張が偽になる変異を注入して全緑かを見る。`または`/`もしくは` で列挙された側は、片方しかテストされていないことが多い。(#62: 「`ok` が false または欠落」の欠落側に正の対照が無く、`!== true` を `=== false` へ弱める変異が全緑)
- **新しい JSDoc の断定文**: 追加された JSDoc・コメントから「常に」「必ず」「一切〜ない」「〜の場合でも同じ」「この経路には来ない」の形の断定文を抜き出し、それぞれが偽になる最小の変異を注入して全緑かを確かめる。全緑なら、その文は実装の性質ではなく作文であり、テストを足すか、断定を落として「未検討」と書き換えさせる。是正タスクが自分の新しい JSDoc で同じ穴を作っていないかを見る。(#70: 「払戻が取込済みでも規則 U は常に判定不能として除外する」と書かれたが、条件に `!racePayoutAvailable &&` を足す変異が全緑。#51 の真因も、JSDoc がレース単位と宣言し、実装が馬単位だったことである)
- **生産者と消費者**: センチネル文字列・argv の順序・終了コードの意味・環境変数のように、一方が出力し他方が解釈する取り決めは、どちらの単体テストにも現れない。両端を実際につなぐテストを要求する。「壊れても CI で落ちるから fail-closed で問題ない」は、落ちること(守られること)と、落ちたときに診断が残ること(別の主張)を混同している。
- **止まった理由**: ゲート・バリデーション・CI 関門は、`status === "block"` を assert して満足しない。その検査が守る実際の破綻を注入して実行し、返る message に原因が含まれるかを目で見る。診断を捨てる検査は、fail-closed でも目的を達していない。(#62: ABI 不一致を注入すると、原因を含むセンチネルが出ているのに終了コード分岐が先に評価されて捨てられ、CI ログには「exit code: 1。stderr: 」だけが残った)
- **写像の検証**: 入力のフィールドを読んで出力のフィールドへ書く変換(View 型への写し取り・候補ビルダー・DTO 変換)は、同じ型の隣接フィールドの取り違えを型検査が検出しない。値を assert したことを、写像を検証したことと等置しない。(1) 読んだ入力フィールド × 書いた出力フィールドの対応表を作る(`grep -o 'row\.[a-zA-Z]*'` 等で機械抽出し、入力型の全フィールドと突き合わせる。出力側も共用体の全枝を数える)。(2) 各行を入れ替え変異で潰す(`number` 群と `number|null` 群を跨ぐ入れ替えも型検査を通る。フィクスチャの数値既定値はグループ横断で相異なることを自己テストで固定する)。(3) 各行について、入力側が複数の異なる値をとるテストがあるかを見る。全行が同じ値だと、出力を既定値の定数にする変異も、別の行の値を使う変異(`.map()` へのリファクタで起きる)も検出できない。判定は、当該出力を定数に置き換えて全テストを流し、全緑なら未検証である。SQL の位置パラメータ(`INSERT ... VALUES (?, ?, ...)` と `stmt.run(a, b, ...)`)は最優先で疑い、列数が 10 を超えるなら、列リストと `run()` の実引数の並びを `grep -o` 等で抽出して機械的に突き合わせてから (1)〜(3) を行う。(D-2c 第2段: `adjustedProb` を `prior` に差し替える変異など 3 種が、順に全緑で残った)
- **全列 `toEqual`**: AC が「全 N 列を `toEqual` で固定」と書いていても、保証されるのは列の書き漏らしが無いことだけである。(1) 同値の対(`wide`/`trio` がともに `"present"` 等)は、2 列の束縛を入れ替える変異が全緑になる。(2) 常に null の列(非 null になる経路のテストが欠けている)は、束縛を `null` リテラルに潰す変異が全緑になる。列 × フィクスチャ値の表で同値の対を洗い、各列が非 null になる経路を型定義・実装から数えて、そのテストが差分にあるかを突き合わせ、空きセルは変異を注入する。全緑なら、フィクスチャの値を列ごとに相異なるものへ変えるか、欠けた経路のテストを足させる。
- **実装由来の定数どうしの比較**: `import { SOME_NOTE } from "実装"` して `expect(view.notices).toEqual([SOME_NOTE])` と書くテストは、expected と actual が同一のバインディングなので、定数の中身が書き換わっても緑である。検査できているのは「分岐がどの定数を参照するか」だけで、「利用者に何が表示されるか」ではない。外部に見える文字列(文言・ラベル・キー名)を返す差分では、`toEqual`/`toBe` の右辺に実装由来の識別子が現れる箇所を grep し、定数ごとにハードコードしたリテラルとの `toBe` が併置されているかを確認し、無ければ定数の定義内容だけを書き換える変異で全緑かを確かめる。「定数どうしが互いに異なる」を `new Set([...]).size` で固定するテストも同じ穴を持つ。(#55)
- **app が組み立て core が保存する二層**: app 側の変換関数のテスト(オブジェクト同士の `toEqual`)と core 側の往復テスト(DB 生行の `toEqual`)が別のフィクスチャを使うと、片方で識別可能な値が、もう片方では同値になる。両層それぞれについて表を作り、app が作った値が DB まで届くことを見る結合テストが 1 本でもあるかを確認する。無ければその継ぎ目は型検査しか守っていない。(#59: core の往復テストが `route="unavailable"` を持たず、`unavailable_reason` を `null` に潰す変異が全緑。AC の「全 20 列を `toEqual`」は守られていたが、値が列を識別していなかった)

## 回帰テストの継承と受け入れ条件の照合

- **回帰テストの継承**: 契約変更で既存テストファイルが大きく書き換えられると、無関係な回帰テストが巻き添えで消える。テスト名の差分(`grep -oP '(?<=it\(")[^"]*' | sort | comm`)は、改称で名前がほぼ全件変わるとノイズだらけになる。旧版を `git show <旧コミット>:<パス>` で取得し、テスト名ではなく「何を保証していたか」(不変条件・設計判断)を列挙して、旧の各項目に「新のどのテストが継承したか / 契約変更で意図的に削除した(理由付き)」の対応表を作り、未分類をゼロにする。「同等のテストがある」という主張は、同じ強度か(既定値しか検証していない・`not.toBe` が無い等の弱体化がないか)を自分で読んで確認する。JSDoc やコメントが「設計判断」「符号規約」「〜の回帰テスト」と明記する性質は、対応するテストが消えていないかを個別に確認する。(C-2: 名前の diff で 4 件の消失は見つかったが、`placeProbSumDeviationは符号付き` の消失は見落とした)
- **AC が名指しする無条件 expect**: AC に「元のテストの無条件 expect をすべて引き継ぐ(`capApplied===true`・丸め後も 2 頭とも正 …)」のように列挙されていたら、列挙を項目に分解して番号を振り、対応するテストの `expect(` 行を `grep -nE 'expect\('` で全部抜き出して、番号ごとに該当行を指す。指せない番号があれば指摘する。「実測したら性質自体は成立しているから実質同じ」は理由にならない(assert しないと、フィクスチャが退化した入力に差し替えられたときテストが黙る)。コピー元のテストから双子を複製した差分は、`diff <(抜粋CB) <(抜粋PL)` でコピー時に落ちた行を探す。(#81: PL 版の AC6 から、CB 版にあった「丸め後も 2 頭とも正」の検査が落ちていた。code-reviewer は 3 回のレビューで検出しなかった)
- **前件と後件**: 「A しても B が壊れないこと」の条件は、A を作る関数のテストがあることを B の検証と取り違えやすい。条件文を節に分解し、後件(壊れない側=下流)を実際に走らせるテストが 1 件ずつあるかを確認する。(#40: 「戦績 0 走になる馬がいても prior が計算できる」に対し、フィルタ関数側のテストだけがあり、下流の `computeFieldPriors` を通すテストが無かった)
- **名前ではなく本体**: `describe("受け入れ条件N: ...")` の見出しは、その条件が検証されている証拠にならない。見出しが名乗る主張と、テスト本体の入力・アサーションが一致するかを 1 件ずつ突き合わせる。条件の主語(何と何を比較するか)と、比較が成立する前提(「キャップ拘束時」を名乗るなら `capApplied===true` が実際に成立するか)を実測する。テスト名が主張する範囲を、テスト行列が実際に覆うか(その条件を破る唯一のケースを含むか)も見る。(C-2: 「比例縮小 vs 貪欲打ち切り」のテストが、キャップが一度も拘束しない設定で別の性質を検証し、AC7 が 5 周のレビューを通過して未実装だった)

## 数と列挙の照合

- **数えられる断定**: JSDoc・コメント・報告・コミットメッセージの「次の 2 箇所」「3 パーサすべて」「全 N 列」は、レビュー時に自分で数えるコマンドを実行して照合する(`grep -rln 'from "./xxx.js"' src | wc -l` 等)。数を間違えた散文はテストを 1 件も落とさないので、変異注入では検出できない。同じ集合を差分内の複数箇所(共有ヘルパの JSDoc・利用側の表・テストのヘッダ)が数えているなら、数どうしの一致も突き合わせる。実装者やオーケストレーターが申告した件数を、数え直さずに報告へ転記しない。訂正報告の数値も実測してから書く。機械抽出は「数詞+助数詞」だけでは足りず、(i) 範囲表現 `N〜M`、(ii) `Nつ`/`N点`/`N組`/`N%`、(iii) 数詞を伴わない網羅・唯一性の断定(`すべて`/`いずれも`/`のみ`/`一切`/`唯一`/`常に`)も走査する。`docs/` も対象に含める。(#34: レビュー 4 巡が数え直しの是正に費やされ、LGTM 後も「4 パーサ全体」が残った。実際は 3 パーサで、grep 1 本で反証できた)
- **自己参照する数**: 差分が新しく書いた散文の中の数は、差分を適用した後の状態で数え直す。「この不変条件テストは N 本」は、その差分が N+1 本目を追加しているときに外れる。(a) HEAD で `grep -c` 等により数え、(b) 同じコマンドをベースコミット(`git show <base>:<パス> | grep -c`)でも走らせ、差が出るなら、本文の数はベース側の数である可能性が高い。(#74: 「総出現数13」と書いた文自身が 14 個目だった。#76: 「テストが 2 本」と書いた同じコミットが 3 本目を追加していた)
- **単位と定義域**: 一致を見る前に、その数が何を数えた数か(単位)と、どこまでを数えたか(定義域)を確かめる。(a) 「N 経路」「N 箇所」「N パーサ」が、定義の数・呼び出し箇所の数・モジュールの数のどれかを本文から確定させる(確定できない語は指摘の対象)。(b) 配線の網羅を主張する数は「呼び出し箇所」の単位で数え直す(`grep -c` は行数、`grep -o ... | wc -l` は出現数で、`return { a: f(x), b: f(y) }` は前者だと過小になる)。(c) 定義域は関数名でなく概念で取り直す。名前での走査は、別名の汎用ヘルパで同じ概念を作る箇所を発見できない。その概念の値が代入されるフィールドで走査する(例: `grep -rn "odds\w*:\s*\(Number(\|numberOrNull\|parseFloat\)"`)。誤りと判明した数詞は、差分の追加行から grep して再発を潰す。(#73: 「5 経路」は定義の数で、呼び出し箇所は 12 あり 3 箇所が無検査だった。汎用 `numberOrNull` で作る別の経路も列挙されず、誤った「5 経路」が新規 JSDoc に書き込まれたまま LGTM が出た)
- **成果物に埋め込まれた検証コマンド**: JSDoc の「`grep -rn "..." path` で確認可能」は網羅性を検算できる点で有効だが、パターンが実装の表現に依存して腐る(`a?.b` を `const x = a; x?.b` に分解しただけで件数が静かに減る)。(a) コマンドをそのまま実行して、本文の件数と一致するかを見る。(b) 同じ集合を別の切り口(識別子だけの広い grep)でも数える。(c) 件数を断定しない散文に検証コマンドだけ添えるのは、腐敗リスクだけが増えるので認めない。(d) 一文が 2 つ以上の数を断定するなら、結論を支える側の数をコマンドが再現するかを見る。(e) コマンドに、文書構造から導かれない定数(バイト窓幅・`head -N`)があれば、その定数を変えて出力が動くかを見る。(#73: 「12 行中、片側だけ数値化できない行は 0 件(再現: … → 12 件)」。根拠は 0 件の側だが、コマンドが出すのは 12 だけで、窓幅を変えると 11 に変わった)

## 数値の再現性

- **実測調査タスクは一次データ**: 調査タスクの成果物は記録そのものなので、数値が正しいかより、その数値を導いた応答・HTML・JSON がコミットされているかを見る。(a) ドキュメントの具体的な数値・件数・差分の主張を 1 つずつ列挙し、各々を repo 内のどのファイルから再計算できるか答える。答えられない主張があれば、値が正しくても指摘する。(b) 「取得したが保存しなかった応答」に基づく主張を疑う(後続の設計判断を左右するなら指摘)。(c) 導出値(算術的帰結)と観測値が見分けられるか。サイトが実際に提示した数も併記されているかを、コミット済みフィクスチャを開いて突き合わせる。(d) ゼロコストで得られる証拠を取りこぼしていないか(D-1: 少頭数レースの `result.html` を取得しながら、同じファイルにあった「複勝の払戻点数が 2 点」の直接証拠が記録されていなかった)。「検証手段のない数値を測定値の口調で書く」問題は繰り返し再発している(必要総資金の倍率・連続最適比率の実測例・出馬表の頭数の数え方・地方 3 連複の軸馬別取得の差分観測・JSDoc 内の性能ベンチマーク)。
- **調査タスクに限らない**: 検証すべきは差分に現れるすべての数値主張で、置き場所(`docs/*.md`/JSDoc/コード内コメント/テスト名・テストコメント)もタスク種別も問わない。`git diff <base> HEAD | grep -E '^\+' | grep -E '[0-9]+(\.[0-9]+)?\s*(ms|秒|件|%|倍)|中央値|平均|p95|実測'` で追加行の数値主張を洗い、各々を repo 内のどのファイル・コマンドで再現できるか答え、答えられないものを列挙して指摘する。

## 永続化スキーマの変更

列を足した migration は、空の DB に全部適用すれば必ず緑になる。テストが新規の DB だけで書かれていると、適用の順序・旧い Worker との共存・新しい Worker が先に出た場合の被害が、全テスト緑のまま通る。本番の D1 は CI にもリポジトリにも存在せず、自動で守られるのは、`scripts/test/cloud-d1-schema.test.ts` の宣言と、`deploy-cloud.yml` の check ジョブが migration をローカルの D1 に適用することまでである。

- **先例の形**: `git diff` に `cloud/migrations/` の新しいファイルが現れたら、`cloud-d1-schema.test.ts` の先例の形を数える。`FILES` の一覧と「後から足すときは次の番号」の注記、`D1_EXTRA_COLUMNS` の宣言(exe の `AnalysisStore` が作る構造に無い D1 専用の列は、ここに無ければ不一致として検出される)、そして 0023・0024 のように、「直前までの migration には列が無いことを固定 → 適用後の列が `D1_EXTRA_COLUMNS` と一致 → 索引が増えない → SQL が `ALTER TABLE ... ADD COLUMN` だけ〈UPDATE なし〉」を 1 件ずつ固定するテストである。新しい migration だけがこの形のテストを持たないなら、既存の慣行からの逸脱として報告する。
- **migration の性質**: 報告の前に自分で確かめる。(a) 追加のみか(`DROP`・`RENAME`・型変更で既存を壊さない。`ADD COLUMN` は既存行を NULL で残す。`UPDATE` で既存行を書き換える文があれば、本番の件数で通るかを別に問う)。(b) 旧い Worker と共存するか(直前のコミットの Worker が発行する INSERT の列リスト・SELECT が新スキーマで通るか。新しい索引・CHECK・UNIQUE が旧 Worker の INSERT を弾く形になっていないか、既存の列の意味や型を変えていないか)。(c) 直前までの migration を空の DB に適用して既存行を 1 件入れ、新しい migration を適用して行が残ること(`schemaAfter` と同じ手で、10 行のスクリプトで済む)。「動くこと」と「テストがあること」を分けて報告する。
- **適用の順序と先行デプロイ**: (a) `deploy-cloud.yml` が `wrangler d1 migrations apply DB --remote` を `wrangler deploy` より前に置いているか(workflow に触れる差分なら、`scripts/test/cloud-deploy-workflow.test.ts` が順序を固定していることも確認する)。(b) 新しい列を読み書きする Worker のコードがあるなら、`cloud/src/d1-health.ts` の `D1_HEALTH_SQL` がその列を指しているか(`/api/health` の `d1.ok=false` が、migration の反映前に新しい Worker が出た状態に気づく唯一の経路)。(c) 新しい Worker が migration より先に動いたら何が落ちるかを列挙する(どの読み出し・書き込みが `no such column` で失敗するか。保存まで壊れるなら、順序を担保する仕組み (a) が実在することを実物で確かめる)。
- **UPSERT の `DO UPDATE SET`**: 新列を足したときは、その列を渡さない呼び出し元がいないかを `grep` で全数確認する(いれば、そちらの再保存が既存値を静かに NULL で上書きする)。production の呼び出し元が 1 本でも、テストヘルパ経由の再保存で同じことが起きうる。
- Issue #100 は exe の SQLite 時代の事例である。当時の移行機構と旧 DB のテストは Issue #400〈R-12a〉で削除したので、当時の手順はもう実行できない。教訓の「既存の慣行から逸脱した新しい変更を、慣行の数え方で見つける」は、D1 の migration にもそのまま当てはまる。(#100: `race_results.win_payout` の追加で、旧 DB を開くテストも冪等性テストも追加されず、code-reviewer も観点に挙げなかった)

## 計測スクリプト・ベンチの入力生成

ベンチ・計測スクリプトが「本番相当」を名乗るなら、入力を作る各段を production の実コードと 1 段ずつ対応付けて報告させる。

- **確率 0**: 本番で到達する値が、その生成器では確率 0 になっていないか。連続一様分布から引くと、クリップ境界(`max(0, x)`/`min(1, x)`)にちょうど一致する値は測度 0 で二度と出ない。本番側がその境界値を実際に生成しているなら(クリップで端点に丸める経路)、生成器は本番の最も難しい入力クラスを構造的に除外している。
- **分布の中心・裾**: コメントの主張と一致するか(「〜付近を中心に」と書いてあるなら、平均を計算して確かめる)。
- **他タスクの判断材料**: その数値が他タスクの判断材料に指定されている場合(メインのゲート合意等)、何を測っていて何を測っていないかを、数値とともに明記させる。

## CRLF と LF

CI は `ubuntu-latest` だけで走る(Issue #248 で Windows ランナーを廃止)。それでも、利用者の checkout は CRLF になりうる。差分にリポジトリ内のファイルを読むテストがあるなら、読み込み直後に改行を LF へ正規化しているかを確かめる。(過去に、`\n` を要求する正規表現がローカルの LF で緑、CRLF の環境で失敗し、実装者もレビュアーも見逃した)
