## 2. プロンプト改善の運用目安(ユーザーに説明済み・記録)
- **回収率より先にキャリブレーション(確率の当たり具合)を見る**。回収率は配当ばらつきで暴れるが、
  3着内率(二項)は素直に収束する。まず100〜200レースでキャリブレーションを確認し、確率推定が
  合ってきたら回収率(300点以上の賭け)で妙味を見る。
- プロンプトを実際にいじる判断は **1版あたり最低200〜300レース**(EVプラス賭け点300前後)。
  A/B比較で優劣を言うには各版300〜500点。少数データで回収率が良く見えても偶然を疑う。
- 中央だけだと週末中心で貯まりにくい。**地方(毎日開催)を分析対象に入れると早く貯まる**。ただし地方は
  条件が違う(#32で中央/地方を分けて見られるようにする狙い)。**偏った時期だけのデータで判断しない**。
- 検証画面の集計件数(includedAnalysisCount)・賭け点数(betCount)を、判断に足るデータ量の目安に使う。

## 4. 技術メモ(横展開の観点)
- 既存の nullable/特殊値の契約(finish_position は中止・除外で NULL、オッズは取消で非数値→null)を、
  新規コード(SQL集約・パーサー)が踏まえているか常に確認する。「値の有無」と「行の有無」の混同、
  SQLの `COUNT(列)` の NULL セマンティクスに注意(#31のバグ原因)。

- 予想印の対抗「〇」は U+3007。LLM が `○`(U+25CB)/`◯`(U+25EF)を出す場合に備え正規化する。
- undici 8 は Node≥22.19 必須で Electron 34(Node 20)と非互換 → net.fetch アダプタ注入+undici ^7 整合で対応済み(既存コミットにあり)。

## 6. 機能D(券種拡張: ワイド・三連複)の前提メモ

機能C-2(複勝の予算配分)の次に着手する。**ユーザーが「ワイドや三連複を好んで買うことが多いので優先度は
高めてほしい」と明示したため、C-3(検証画面での回収率比較)より優先する。**

### なぜ必要か(ユーザーの指摘)
> 実際には複勝でなくとも馬券の種類(三連単、三連複、ワイド)によっては馬券に絡んでくる馬なので、
> 買い方の提案を追加する以上は複勝圏内かどうかを考えるだけでは不足していると思われる

### 技術的な到達可能性(調査済み)
- **的中確率は追加モデルなしで計算できる。** 機能C-1 の `PlaceJointModel`
  (`packages/core/src/ev/place-joint-model.ts`)は「どの馬の組合せが複勝圏内に入るか」の同時分布を
  列挙しているため、ワイド(2頭とも3着以内)・三連複(その3頭が3着以内)の的中確率はそのまま導ける。
- **不足1: オッズ取得。** 現状は中央 `api_get_jra_odds.html?race_id=...&type=1&action=init`、
  地方 `odds/index.html?type=b1&race_id=...` の単勝・複勝1系統のみ(`scraper/urls.ts`)。
  ワイド・三連複のオッズは取得URL・パーサの新規実装が必要。
- **不足2: 三連単は原理的に不可。** 着順の情報が必要で、現在の同時分布モデル(どの集合が上位k に
  入るか)では扱えない。Phase 2 の厳密モデル(Plackett-Luce)導入後に再検討する。

### 出走頭数と発売条件(**推測せず実測すること**)
ユーザーからの情報(**閾値は未確定。下記のとおり実測すること**):
- **枠連(地方競馬では枠連・枠単)は枠順で的中を判定する馬券のため、出走頭数が少ないと発売されない。**
  閾値についてユーザーは当初「8頭未満で発売なし」と述べ、後に「7頭未満だったかもしれない」と訂正した。
  **どちらが正しいかは未確定であり、この文書の数字を根拠にしてはならない。** 機能D で券種ごとの
  発売条件を実測する際に、この閾値も併せて確定させること(境界付近の実レース、例えば7頭立て・8頭立ての
  出馬表とオッズページを実際に取得し、枠連が発売されているかを目で確認するのが確実)。

複勝の発売条件(8頭以上=3着まで / 5〜7頭=2着まで / 4頭以下=発売なし)とは券種ごとに異なるため、
**券種ごとの発売条件を必ず実測してから実装する**。過去に地方の重賞判定バッジを推測せず実取得して
事故を防いだ実績がある(`docs/lessons-learned.md` の「良い実践の記録」)。機能C-2 では 7頭以下の
レースを対象外としているが、この扱いは機能D で券種ごとの条件を実測してから改めて決める。

### 設計上の申し送り
- `HorseAllocation`(1頭1買い目)の型は、ワイド・三連複では**買い目が馬の組**になるため一般化が必要。
  機能C-2 で型を作り直す際、馬単位を前提にした命名を避けておくと拡張しやすい。
- 複数券種にまたがる予算配分は、複勝内の配分より難しい問題を含む(同じ馬に複勝とワイドで重複して
  張る扱い、券種間の相関)。機能C-2 の実物を触ってから設計を決める。

### 移行するとしたら影響が大きい箇所(調査時の出発点)
- **better-sqlite3**: ネイティブ依存。Cloudflare Workers では動かない(D1 等への置換が要る)。

- **レート制限**: `http-client.ts` の1.5秒間隔はプロセス内の状態。分散実行すると保証が崩れる。
