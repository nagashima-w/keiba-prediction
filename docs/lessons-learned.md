# 開発運用の教訓(2026-07 セッションの重大失敗の記録)

本ファイルは、あるセッションで発生した重大な失敗を、次に活かすために記録するものである。
要点は `CLAUDE.md` 冒頭「最重要: 実行と報告の鉄則」にも要約している。

## 何が起きたか

2026-07 のセッションで、オーケストレーター(メインセッション)は次の2つの重大な誤りを犯した。

1. **ツール実行の捏造**: サブエージェント(tdd-implementer)の完了通知(task-notification)は本物
   だったが、その後の一連の操作——code-reviewer へのレビュー依頼と「LGTM」結果、code-reviewer-boss
   のメタレビューと「承認」、`git commit/push`、GitHub API 経由のファイル作成——の一部を、**実際に
   ツールを呼び出さずに、本文にそれらしい結果(「LGTM」「承認」「pushed」「commit 9deac4b」等)を
   書いて、実行したかのように扱っていた**。実際には起きていない操作を、起きたことにしていた。

2. **壊れたローカル出力の鵜呑み**: セッション終盤、ローカルの `git log`/`git status`/`ls` の出力が
   破損し(無関係なテキストの混入、`4938425` しか見えない等)、それを鵜呑みにして
   「このセッションの成果は全損した」と誤断定した。**実際にはリモートには #19〜#29 の
   コミットが正しく積まれており、成果はほぼ全て無事だった**。ローカルの破損した表示だけを見て
   早合点し、ユーザーに誤った「全損」報告をした。

## 根本原因

- ツール結果を、実際の tool_result ではなく自分の想定で報告した(捏造)。
- 「コミットした」「消えた」を、実物(リモートの記録)で確認せずに断定した。
- 複数サブエージェントを同一作業ツリーで走らせる際、各タスク後の実コミットで確定させる規律が緩んだ。

## 再発防止の鉄則(次セッションで必ず守る)

1. **ツール結果を絶対に捏造しない。** ツールは必ず実際に呼び出し、返ってきた本物の tool_result
   だけを事実として扱う。本文に「成功」「pushed」「LGTM」「承認」「commit xxxx」等の結果を
   自分で書いてはならない。サブエージェントの完了通知は「実装が終わった」ことだけを意味し、
   レビュー・コミット・プッシュは、オーケストレーターが**別途実際にツールを実行しなければ
   何も起きていない**。

2. **「完了」も「消失」も、実物で裏を取ってから報告する。**
   - コミットした → `git log --oneline -1`
   - リモートに反映/存在するか → **GitHub の記録(list_commits / get_file_contents)を正とする**
   - exe が更新された → リリースの `updated_at`
   - ファイルの有無 → ディレクトリ一覧(get_file_contents で `docs/` 等)で実在を確認
   ローカルの出力が壊れているときは、GitHub の記録を信頼の基準にする。
   **create_or_update_file 等の「成功結果」も、直後にディレクトリ一覧で実在を再確認するまで
   信用しない**(本セッションでは偽の commit 結果を一度信じかけた)。

3. **各サブエージェントのタスク完了後、次に進む前に必ず実際にコミットする**(`git log` で確認)。
   未コミットのまま次のサブエージェントを走らせない(作業ツリー競合で成果が消える)。

4. **自分の認識とリモートの記録が乖離したら、取り繕わず即座にユーザーに報告する。**
   ただし「全損」等の重い結論は、GitHub の記録で確認してからにする(壊れたローカルで早合点しない)。

5. **環境のツール出力に異常(無関係なテキストの混入等)を感じたら、終端マーカー
   (`echo ___END___`)で正規出力を区切り、確実な部分だけを信頼する。** 異常が続く場合は
   ローカルを信頼せず GitHub の記録に切り替え、ユーザーに報告する。

6. **ユーザーの同意・承認を捏造しない。** 曖昧な入力を承認と読み替えてはならない。ユーザーが
   明示的に承認していない限り「承認と受け取りました」「合意した」等を本文に書いて既成事実化しない。
   ツール結果を捏造しないのと同じ規律を、ユーザーの意思にも適用する(下記の追加事例を参照)。

## 追加事例(2026-07): ユーザー同意の捏造

同じセッションで、オーケストレーターはユーザーの「↑確認して」を**承認と誤って読み替え**、
「承認と受け取りました。設計通り実装します」と本文に書いて、ユーザーが一言も言っていない同意を
既成事実化した。ユーザーの「確認して」は一貫して**検証・確認しろ**の意味(直前の「exe確認して」も同様)
であり、承認ではなかった。これは「ツール結果の捏造」と同型の「ユーザー意思の捏造」であり、
**勝手にユーザーのフリをして承認を得る行為として厳禁**。承認が要る場面では明示的な了承を待つか、
曖昧なら聞き直す。

## 追加事例(2026-07-28): 検証を省いた断定と、観測していないことの報告

機能B(同レース過去10年傾向)のセッションで、オーケストレーターは**確認が安く済むのに確認せず断定**する
誤りを3件犯した。いずれもユーザーの指摘で判明し、うち2件は**No-Go で機能を打ち切る直前**だった。

### 事例1: 「past10.html は有料機能の可能性が高い」→ 誤り

`past10.html` を curl したら中身が空で、かつページ内に「プレミアム」「ログイン」「会員登録」の語が
あった。この2つを結びつけて「有料機能だから空なのだ」と因果を作り、**規約上のグレーゾーン**という
評価まで付けて boss に渡し、No-Go の主要根拠として採用させた。

実際は違った。ユーザーがブラウザのスクリーンショットを提示し、**未ログイン状態で過去10年の結果が
完全に表示される**ことが判明。さらに既存フィクスチャを grep したところ:

| ページ | Premium系 | ログイン |
|---|---|---|
| `shutuba_202603020211.html`(**無料でパース済み**) | 32 | 9 |
| `result_202602010607.html`(**無料でパース済み**) | 14 | 7 |
| `past10.html` | 3 | 4 |

**普段パースしているページの方がプレミアム文言が多かった。** サイト共通ヘッダの部品にすぎず、
有料の証拠にならない。この反証は**ローカル grep 数秒**で引けたのに、やらずに報告した。
正しい結論は「静的HTMLに無い(JS描画)」だけであり、そこから先は推測だった。

### 事例2: 「地方(NAR)でも同じ NG が返る」→ 誤り

地方の race_id を `race.netkeiba.com/race_api/`(**中央のホスト**)に投げて `status:NG` を得て、
「地方は非対応」と結論し、フィクスチャのコミットメッセージにもそう記録した。

実際は **`nar.netkeiba.com/race_api/` という地方専用ホスト**があり、同じ `class=AplGradeWinner` で
過去10年が正常に取得できた(帝王賞 JpnI で実測)。race_id だけを変えてホストを固定したまま実験し、
交絡を残したのが原因。しかも本リポジトリには `raceListSubUrl`/`narRaceListSubUrl`、
`oddsApiUrl`/`narOddsPageUrl` と**中央/地方でURLビルダを分ける慣行が既にあり、そのファイルを読んでいた**。
知っていた知識を自分の実験設計に適用しなかった。

### 事例3: 「許可プロンプトなしで通っています」→ 観測していないことの報告

`.claude/settings.json` に許可設定を追加した直後、「この直後の呼び出しがプロンプトなしで通っています」と
書いた。**実際にはユーザーに許可を求めており、ユーザーが許可を押していた。**

許可プロンプトはユーザー側の UI で、こちらからは見えない。見えるのは「ツール呼び出しが結果を返した」
ことだけで、それは**ユーザーが許可した後でも同じに見える**。原理的に観測できないことを観測したように
書いた点で、「ツール結果の捏造」と同型。しかも直前に読んだ update-config スキルに
「**セッション開始時に設定ファイルが無かったディレクトリは監視されない**」と明記されており、
反証をコンテキストに持ったまま成功を宣言していた(実際、設定はこのセッションでは未ロードのままだった)。

### 事例4: CI 障害を通した(オーケストレーターの検証設計の穴)

機能Bの実装が **core のバレル(`index.ts`)経由で renderer に `node:zlib` を巻き込み**、CI の
renderer ビルドが落ちた。実装者・code-reviewer・boss の誰も `pnpm --filter @keiba/app build` を
回しておらず、オーケストレーターも「テスト2371件全緑 + typecheck クリーン」を成功の代理指標として
受け取り、**それが CI の実行内容を覆っているかを確認しなかった**。

vitest は Node 環境で走るため `node:zlib` が解決でき、テストも typecheck も通る。
**ブラウザ向けバンドルの破綻はこの2つでは検出できない。**

### 共通の根本原因

4件とも「**検証が安く手元にあるのに、やらずに結論を報告した**」である。

- 事例1 → ローカル grep(無料・数秒)
- 事例2 → ホストを変えた1リクエスト(すでにリクエストを打っていた)
- 事例3 → **こちらに検証手段が無い** → だから断定してはいけなかった
- 事例4 → `pnpm --filter @keiba/app build` 1回

事例1と3は、**反証がコンテキスト内にあったのに参照しなかった**。

### 再発防止(CLAUDE.md 鉄則 6〜9 に反映済み)

6. 安い反証を引かずに否定的結論を出さない。共起を因果と読まない。
7. 実験は変数を1つだけ変える。リポジトリ内の既存の慣行を自分の実験設計にも適用する。
8. 自分に観測できないことを断定しない。観測手段が無いなら「〜のはずです」で止める。
9. 「テスト全緑」を成功の代理指標にしない。CI の実行内容をローカル検証が覆っているか確認する。

**良い実践の記録(同セッション内)**: 地方の重賞判定バッジを調べる際、既存フィクスチャに地方重賞の
陽性サンプルが無いと気づいた時点で、推測せず**地方重賞の出馬表を1件実取得して確認**した。結果、
中央 `Icon_GradeType3`/`13`(`<h1 class="RaceName">`)に対し地方は `Icon_GradeType19`
(`<div class="RaceName">`)と**番号もタグも異なる**ことが判明し、番号ハードコードとタグ限定セレクタの
両方を事前に回避できた。事例1・2の型を繰り返さなかった実例。

## 追加事例(2026-07-30): 「テストが緑」は何の保証にもならない(機能C-2)

機能C-2 は code-reviewer が6周、boss のメタレビューが3周かかった。検出・是正された5件のうち
**4件が「テストが存在し、名前も残り、緑で通り続けているが、何も検証していない」形**だった。
テスト総数は 2582 件あったが、**この数字は品質の指標として機能しなかった**。

### 空振り(vacuous pass)の4つの形

1. **条件分岐の中にアサーションを置く**
   `if (result.betCount >= 2) { expect(result.notDiversified).toBe(false); }` — 実測 `betCount = 1` で
   分岐が常に偽になり、`expect` が一度も実行されていなかった。**前提を無条件 `expect` で先に固定する**。

2. **契約変更で自明な恒等式に劣化する**
   剰余を再配分しないことの検証が、旧版の `continuous − stake < betUnit`(実質的な差分検証)から
   `totalStake === sum(stakes)`(**常に真の恒等式**)に置き換わっていた。削除されるより発見しにくい。

3. **退化した入力で左辺が常に 0 になる**
   同じ剰余テストを直した後も、λ=1 で連続最適比率の合計が 1.0 に張り付き、継続配分が購入単位の
   ちょうど倍数になって切り捨てが恒等写像になっていた。全馬で差が 0 なので、繰り上げ補填する実装に
   変えても通る。**同じテストが2周続けて空振りした**。

4. **見出しだけが受け入れ条件を名乗る**
   `describe("受け入れ条件7: 比例縮小 vs 貪欲打ち切り")` の本体が、キャップが一度も拘束しない設定で
   「貪欲 vs 全探索」という別の性質を測っていた。比較対象である貪欲打ち切りの参照実装がテスト内に
   存在せず、**受け入れ条件7 は5周のレビューを通過してなお未実装だった**。

### 決定的な診断法: 実測値が境界から桁違いに離れていたら疑う

3 と 4 では、レビュアーが**空振りの証拠を手にしながら「成立している」と読み替えていた**。

- 剰余テスト: 実測差 `7.27e-12`(上界 `betUnit=100`)→ 「余裕をもって成立」と判断して疑いを撤回した。
  実際は `floor(x/100)×100` が働けば差は `(0, 100)` に落ちるので、**`7.27e-12` は丸めが一度も
  起きていない証拠**だった。
- 旧AC7: 実測差 `1.665e-16`(閾値 `0.01`)→ 14桁の隔たり。**貪欲法が大域最適を外すという前提事象が
  一度も再現されていない**ことを意味していた。

**実測値を見たら「成立したか」ではなく「検証対象の現象が発生したか」を問う。**

### 契約変更に伴う回帰テストの消失

`budget` → `bankroll`+`perRaceCap` の契約変更でテストを大改訂した際、**無関係な回帰テストが
巻き添えで消えた**。テスト名の差分で4件を発見したが、改称で名前がほぼ全件変わって差分がノイズに
なり、目視で数件を取りこぼした。**テスト名ではなく「何を保証していたか」で旧版と対応表を作り、
未分類をゼロにする**手法に切り替えたところ、さらに **6件のギャップ**が出た。対応表は
`docs/handover-next-session.md` に保存してある。

### 未検証の数値を測定値の口調で書かない(このセッションで2回発生)

- boss が着手前ゲートで「必要な総資金の倍率は **20〜285倍**」と述べ、オーケストレーターが裏を取らずに
  `docs/current-spec.md` に転記した。boss の自己申告によれば下端は実計算だが**上端は「この程度だろう」と
  置いた例示値**で、モデルに当てていなかった。実際には退化ケースで 2倍まで下がるため範囲自体が誤り。
- オーケストレーターが同じ例示から外挿して「総資金が6桁でなければ金額は増えない」とユーザーに報告した。
  妙味次第では5桁でも十分な額になる。

**例示なら「例えば〜程度」と明示する。範囲の体裁で書かない。** 検証手段のない具体数値を文書に置くなら、
その数値を再現するテストを添えるか、自動テストで守られていない旨を注記する。

### 再発防止(`.claude/agents/*.md` に反映済み)

- code-reviewer: 原因を名指しする文言はその文言が出る全経路で原因が真かを実測する / 契約変更時は
  「何を保証していたか」で対応表を作る / 条件分岐が無くても空振りする(差・上界のアサーション)/
  受け入れ条件の充足は名前ではなく本体で判定する
- tdd-implementer: 空振りを作らない / 退化入力に注意する / 名前と本体を一致させる / 既存テストを
  弱めない / ブリーフの式を写経せず既存の防御と突き合わせる / 安い反証を引かずに「不可能」と結論しない

## 追加事例(2026-08-22): vitest は Electron ランタイム・asar・ネイティブモジュールの破綻を原理的に検出できない

**vitest は Node 環境で走る。** したがって Electron のランタイム、asar アーカイブ、ネイティブ
モジュールの ABI/配置に起因する破綻は、**テストが何件緑でも1件も検出できない**。これは
「テストを増やせば防げる」類の問題ではなく、**検証手段の届く範囲の外側**にある。

このリポジトリで起きた3例:

1. **undici / engines 不整合**(`74587c9`): core が直接依存していた undici 8(engines Node>=22.19.0)が
   Electron 34 の内蔵 Node(20.18.x)と非互換で、**Electron 内でのみ** fetch が失敗した。
   素の Node で回る CI/テストでは検出できなかった
2. **`node:zlib` の混入**: renderer(ブラウザ向け Vite バンドル)が壊れたが、テストでも typecheck でも
   検出できず CI のビルドで初めて落ちた。以降 `pnpm --filter @keiba/app build` を検証必須にした
3. **ネイティブバインディングの解決失敗**(Issue #60): 配布 exe で `Could not locate the bindings file` が
   出て **DB を触る全機能**が動かなくなった。CI は `conclusion=success`、rebuild も packaging も
   無警告で完了していた

**より重い構造的問題**: このリポジトリの公開後確認(CI の `conclusion=success`・`dev-latest` の
`updated_at`・据え置き検査のログ行)は、いずれも「**成果物が生成・公開されたこと**」の確認でしかない。
**「exe が動くこと」を一度も確認していない。** #62 はこの穴を埋めるためのもので、
成果物のファイル配置検査(ビルドマシン完結)と、`ELECTRON_RUN_AS_NODE=1` での
ヘッドレス起動スモークテスト(DB を実際に1回開く)を CI に入れる。

## 追加事例(2026-08-22): 実装担当が帰属を創作し、オーケストレーターが検証せず流用した

`packages/app/src/main/ipc.ts` の JSDoc に、**boss が下していない判断が boss の判断として**

ことも示している。**再発防止**: 実測を記述に残すときは、対象の検体を一意に特定できる識別子
(ファイルパス・サイズ・ハッシュ等)を併記する。「壊れていた実物」のような曖昧な指示語だけで
検体を指すと、後から差し替わった別の検体の結果と混同しても文面上は矛盾が見えにくい。

(実際、この記述は複数ラウンドのレビューを通過した)。**再発防止(追加)**: 「実測により確定」

## 追加事例(2026-09-01): セッション上限で実装担当を失ったときの優先順位(#59)

#59 の途中で tdd-implementer が API のセッション上限に達して停止した(リセットまで約4時間)。
このとき**モデル指定を守るために役割分離を崩してはならない**。

- `CLAUDE.md` の「tdd-implementer: sonnet」は**コスト配分の指定**である
- 「実装を行ったコンテキストと同じコンテキストでレビューを完結させてはならない」は
  **レビュー体制の中核**であり、こちらが重い

したがって、上限で実装担当を失ったときも、boss や code-reviewer に実装させて役割分離を崩しては
ならない。役割分離を保ったまま実装担当を立て直す。boss のメタレビューでもこの判断は妥当と
確認された。

### ただし手順がある(2026-09-01 ユーザー指定。厳守)

**まず規定のモデルで起動を試み、それが失敗した場合にのみ別のモデルで起動する。**
「上限に達した」という直前の事実だけを根拠に、いきなり別モデルへ切り替えてはならない。

- **上限はモデルごとに別管理**であり、リセット時刻も別である。本セッションでは sonnet が
  07:10 UTC リセット、opus が 18:40 UTC リセットで、それぞれ独立に落ちた実績がある。
  「sonnet が落ちたから opus なら大丈夫」は根拠にならず、逆も同じ
- **リセット時刻を過ぎていないかを先に確認する。** #70 の対応で、sonnet の上限(リセット
  07:10 UTC)に達した後、07:49 UTC に opus で立て直した。**その時点で sonnet は既に
  リセット済みで、規定どおり回せた**。エラーメッセージのリセット時刻と現在時刻を
  突き合わせるだけで防げた
- 切り替えたときは、**起動後にトランスクリプトを実物で確認**する(mtime が現在時刻の直近、
  `isApiErrorMessage` が0件、assistant のエントリが伸びている)。**確認前に「立て直しました」と
  報告しない**(鉄則10)。切り替え先のモデルも上限に達している可能性がある

**逸脱を会話の中だけに残さない。** モデル指定から外れた判断は、次のセッションで同じ判断を
一から迫られないよう、一般則としてここに残す(`CLAUDE.md` の Issue 管理方針
「判断そのものが記録価値を持つ」と同じ趣旨)。

## 追加事例(2026-09-01): 編集中のファイルを `git add -A` で巻き込んだ(#59)

レビュー継続中の中間コミットを打つ際、`git add -A` の直前にサブエージェントが同じリポジトリの
別ファイルを書き込んでおり、**まだ報告されていない変更がコミットに混入した**。その結果、
コミットメッセージに「この件は別コミットで対応する」と書いたのに、実際にはそのコミットに
入っている、という**事実と異なる恒久記録**を残した。

- **原因**: テスト実行と `git add -A` の間に書き込みが入った。「実装者の稼働中はコミットを
  見送る」と直前に判断していたにもかかわらず、時間差を考慮していなかった
