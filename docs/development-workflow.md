# 開発ワークフロー(導線・要約)

本書は開発の進め方(サブエージェント体制・レビュー・報告方針)の**導線と要約**であり、
規約の**唯一の正は [`CLAUDE.md`](../CLAUDE.md)**。齟齬がある場合は常に CLAUDE.md を優先する。
各サブエージェントの詳細な指示は `.claude/agents/*.md` を参照(本書はそれらを相互参照でまとめたもの)。

## 体制(4 つの役割とモデル)

| 役割 | モデル | 担当 | 定義 |
|---|---|---|---|
| プロジェクトマネジメント役(メインセッション) | fable または opus | ユーザーと直接会話、仕様確認・進行管理・指示。**実装/レビューはしない**。サブエージェント間の**やり取りを中継**する | CLAUDE.md「エージェント体制」 |
| tdd-implementer | sonnet | 機能実装・バグ修正・レビュー指摘の修正。TDD を厳守 | `.claude/agents/tdd-implementer.md` |
| code-reviewer | sonnet | 批判的コードレビュー(一次判断)。実装には関与しない | `.claude/agents/code-reviewer.md` |
| boss | opus | (1)着手前ゲート と (2)敵対的メタレビュー。差し戻し再発防止のため code-reviewer.md を改訂する権限を持つ | `.claude/agents/boss.md` |

- サブエージェント同士は直接通信できない。boss ↔ tdd-implementer 等の往復は**必ずメインが中継**する。

## 手続き(着手前ゲート → TDD → 2 段レビュー → コミット)

1. **タスク案作成**: メインが仕様/指示から次の 1 機能を選び、受け入れ条件を整理する。
2. **着手前ゲート(boss)**: boss がタスク案を仕様・CLAUDE.md と突き合わせて精査し、曖昧点・合意論点・
   TDD で固める境界値を整理。tdd-implementer の確認(メイン中継)と往復し、合意で **【Go】** を出す。
   Go が出るまで tdd-implementer は実装に着手しない。
3. **TDD 実装(tdd-implementer、必須)**: **Red**(先にテストを書き失敗を実行確認)→ **Green**(最小実装で
   成功を実行確認)→ **Refactor**。テスト実行結果(失敗→成功)を必ず報告する。不確実点があれば実装せず
   メインに確認して指示を仰ぐ。テストフレームワークは vitest。scraper のテストは `fixtures/` に対して行い
   実サイトへはアクセスしない。バイアス計算は境界値(2 走未満で補正なし等)を含むテーブル駆動テストを書く。
4. **一次レビュー(code-reviewer)**: 実装完了ごとに起動し、自分で `git diff` を読みテストを実行して
   批判的にレビュー。指摘は【重大】【要修正】【提案】に分類。指摘ゼロのときだけ LGTM。
5. **修正の往復**: 【重大】【要修正】は tdd-implementer(同セッション継続)が修正し 4 に戻る。
6. **メタレビュー(boss)**: LGTM が出たら**同一 boss** が敵対的に検証(差分を自分で読み、合意スコープ
   逸脱・観点の抜け・検証の形骸化を探す)。差し戻しがあれば 4(必要なら修正)に戻る。**boss の承認まで
   次の機能に進まない**。
7. **コミット**: boss 承認後にメインが**実際にコミット**し、`git log`(または GitHub の記録)で反映を確認。

> **実装完了 ≠ レビュー・コミット完了。** サブエージェントの完了通知は「実装が終わった」ことだけを意味し、
> レビュー(code-reviewer/boss)・コミット・プッシュはメインが**別途実際にツールを実行しなければ何も
> 起きていない**。結果を捏造しないこと(CLAUDE.md 冒頭「最重要: 実行と報告の鉄則」、詳細は
> [`docs/lessons-learned.md`](./lessons-learned.md))。

## セッション運用(タスク単位)

- 3 種のサブエージェント(tdd-implementer / code-reviewer / boss)は**タスク単位**で運用し、無関係な
  過去タスクのコンテキストを持ち越さない。
- 1 タスクの間は各セッションを保持し `SendMessage` で往復してよい(同一 boss が着手前ゲートと最終メタ
  レビューを一貫して担うのが望ましい)。
- **タスク完了(コミット確認まで)したら 3 体のセッションを破棄**し、次タスクは新規起動する。
- 未コミットのまま次のサブエージェントを走らせない(作業ツリー競合で成果が消える)。

## 報告と承認の方針

- 着手前ゲート → 実装 → レビュー → コミットまでメインは**自律で進めてよい**(各ステップの逐一報告は不要)。
- **課金が発生する操作は事前にユーザー承認**を得る: 実 Claude API を使う分析・動作確認、netkeiba への
  まとまった実リクエスト等。フィクスチャベースの開発・テストは課金がないため承認不要。
- **節目(タスク完了・exe 更新等)で軽く進捗報告**する。
- **コミット・プッシュ後は毎回 exe 再ビルドを実物で確認して報告**(ユーザー指定): CI
  (`build-windows.yml`)の該当 run が `conclusion=success`、かつ `dev-latest` の exe の `updated_at` が
  プッシュ後であること。完了に時間がかかるため未完なら完了を待って追う。CI 失敗時は原因を調べて報告。
  - **例外**: コミットメッセージに「レビュー継続中」を含む中間コミットでは、CI が `dev-latest` への
    公開と孤児 exe 掃除を**意図的にスキップ**する(ログに `::notice::` が出る)。この場合は
    `conclusion=success` のみを確認し、**exe の `updated_at` は確認対象にしない**(更新されないのが
    正しい)。exe の実物確認は boss 承認後の最終コミットに対して行う。詳細は `CLAUDE.md`
    「レビュー継続中の中間コミット」。
- ユーザーの同意・承認を捏造しない(「確認して」は検証の意味であって承認ではない)。

## 言語規約

- コードコメント・ドキュメント・コミットメッセージ・テスト名(describe/it)はすべて日本語。
- 変数名・関数名は英語(通常の TypeScript 慣習)で良い。
