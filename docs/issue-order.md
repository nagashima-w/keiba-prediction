# Issue の着手順

**次に何をやるかは、このファイルを見れば分かる。** セッションが切れて会話の文脈が失われても、ここと GitHub Issue が残る。

最終更新: 2026-08-22(#60 系列の起票・#61 完了時点)

## 読み方

- 上から順に着手する。同じ節の中では番号順ではなく**記載順**が着手順
- 「前提」がある項目は、その前提が完了するまで着手しない
- 完了したら Issue をクローズし、**このファイルからも消す**(open な Issue とこの一覧が食い違ったら、GitHub の方が正)
- 着手しないと決めたものも理由とともに残す。**判断そのものが記録価値を持つ**

## 優先順位の原則(ユーザー指定)

> ワイドと三連複の対応に着手してからはこれらに対応するのを優先して他のissueより先に対応して

**券種拡張シリーズを他の Issue より優先する。** 全体像と技術的な依存関係は **#22** に集約。

例外として **#20**(同時分布モデルの厳密化)は馬単・三連単の技術的前提なのでシリーズの一部として扱う。

**着手前ゲートの実測で判明した重要な事実**: 実物の配布 exe を検査したところ、`.node` は
`app.asar.unpacked` に**正しく展開されており**、実物の Windows asar に Electron のランタイムで
`require` を通すと `bindings` は**正しい `.node` まで到達した**。つまり**報告されたエラー文と
公開されている成果物の中身は整合しない**。却下した4案(`.npmrc` の `node-linker=hoisted` /
`files` 明示 / `asar: false` / `asarUnpack` 変更)とその理由は #60 のコメントにある。

**#61 は「修正」であると同時に「診断」である。** 直らない可能性があり、直らなかった場合は
エラーの文面が変わるので原因を一発で確定できる。

**構造的な問題**: このリポジトリの公開後確認は「exe が更新されたこと」しか見ておらず
「exe が動くこと」を一度も確認していない。詳細は `docs/lessons-learned.md`(2026-08-22 の2項)。

## 2. 確率の質(#35 系列)

券種拡張とは独立した問題だが、**券種を増やしても確率が無情報なら EV はオッズの順序をなぞるだけ**になるため、放置はできない。ただし優先順位は券種拡張の下。

| 順 | Issue | 内容 | 前提 |
|---|---|---|---|
| 12 | **#39** | 過去レースを分析すると、そのレース自身の結果が戦績に混入する(先読みリーク)。**本番経路の是正** | — |
| 13 | **#41** | #35-1b: サンプルを拡大して確率の質を測定する(中央20+地方10)。**LLM を使う場合はユーザーの事前承認が必要**(課金) | #40(完了済み), #39 |
| 14 | **#42** | #35-2: 較正の要否と方式を決める。**着手しない結論もあり得る** | #41 |
| — | **#35** | 親 Issue。#41 / #42 の結論が出たら本文を更新して閉じる | #42 |
| — | **#36** | 貪欲法の刻み幅 `greedySteps` が券種構成比を左右する。**#35 の較正と交絡するため、較正の見通しが立ってから** | #42 |

**#42 の判定基準**: #41 の Brier スコアの Murphy 分解。**resolution ≈ 0(識別力なし)なら、どんな較正をしても市場超えの回収率は原理的に出ない** → #42 は「較正」ではなく scorer の作り直しとして再定義が必要になる。
