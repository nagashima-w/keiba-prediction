# Issue の着手順

**次に何をやるかは、このファイルを見れば分かる。** セッションが切れて会話の文脈が失われても、ここと GitHub Issue が残る。

最終更新: 2026-09-01(#71 クローズ時点。#54 系列 完了)

## 読み方

- 上から順に着手する。同じ節の中では番号順ではなく**記載順**が着手順
- 「前提」がある項目は、その前提が完了するまで着手しない
- 完了したら Issue をクローズし、**このファイルからも消す**(open な Issue とこの一覧が食い違ったら、GitHub の方が正)
- 着手しないと決めたものも理由とともに残す。**判断そのものが記録価値を持つ**

## 0. 実機バグ(#60 系列)— **症状は解消。ただし真因は未確定**

配布 exe で better-sqlite3 のネイティブバインディングが解決できず、**DB を触る全機能**が
動かないとユーザーから報告された(2026-08-22、v1.3.1)。**#61 を v1.3.2 として公開し、
ユーザーの実機で「取得」が成功したことを確認した**(#60 / #61 ともクローズ済み)。

### 交絡は解けた。**#61 のコード変更が効いた**

一度は「`%TEMP%` の削除と v1.3.2 の起動を同時に依頼したため切り分け不能」としたが、
ユーザーに確認したところ **`%TEMP%\keiba-ev-tool` は削除していなかった**。
したがって意図的に変えた変数は **v1.3.2(#61 の `nativeBinding` 明示指定)だけ**である。

**boss の検査と実機の食い違いにも説明がついた。** `bindings` は**呼び出し元のスタック
トレースからモジュールルートを推測する**。boss が実測したのは実物 asar への**直接 require**
であり、**実機で失敗していたのは packaged された `main.cjs` の中から呼ばれたとき**である。
呼び出し経路が違えば歩き上がりの起点も変わる。報告された `module_root` が `app.asar`
(asar 直下)だったことは、`app.asar/dist/main` から上へ辿った結果として整合する。
つまり「成果物は正しい」と「実機で解決に失敗する」は矛盾していなかった。

**教訓(#62 の設計に直結)**: #60 当時、`bindings` は呼び出し元のスタックから解決していたため、
直接 require では症状を再現できなかった。**ただしこの制約は #61(`nativeBinding` の明示指定)で
失効している** — `nativeBinding` を渡すと `bindings` は呼ばれず、`.node` の require は
`better-sqlite3/lib/database.js` が絶対パスで行うため、**呼び出し元のスタックはロード可否に
影響しない**(#62 の着手前ゲートで実測)。したがって #62 のスモークは「本番と同じ**呼び出し経路**」
ではなく「本番と同じ**メカニズム**(本番と同一の `resolveVerifiedNativeBindingPath` を再利用し、
`nativeBinding` を明示指定する)」を追う設計になっている。

**この記述は 2026-08-25 に是正した。** 元は「スモークテストは可能な限り本番と同じ呼び出し経路で
叩くこと」という**失効した要件**が、`#62 の設計に直結` という体裁で残っていた。#62 の成果物は
実際にはメカニズムを追う設計であり、指示と成果物が矛盾していた。**#63 が #62 完了後に控えており、
次のセッションがこの失効要件に従う経路が実在した**ため、boss が最終メタレビューの承認条件として
是正を求めた。同種の「前提が変わったのに残った記述」が #62 中に4回発生している
(`docs/lessons-learned.md` の 2026-08-25 の項)。
