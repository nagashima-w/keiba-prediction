# 版数運用規約

本書は root(`package.json`)・`packages/app`(`@keiba/app`)の版数(semver)をいつ・誰が・どの区分で
上げるかを定める(Issue #44-D-1)。

## 背景: なぜこの規約が要るか

exe のファイル名は `packages/app/electron-builder.yml` の
`artifactName: keiba-ev-tool-${version}-portable.${ext}` により `packages/app/package.json` の
`version` から作られる。ところが版数は 2026-08-04(コミット `b99d10e`)に 1.0.0 → 1.1.0 へ手で
上げられて以来、94 コミット据え置かれていた。その間に組み合わせオッズ取得(D-2b)・券種横断の
予算配分(D-2c 第1〜4段)・確率の質の計測基盤という明確な機能追加が入った。**「手で上げる」運用は
既に一度確立され、そして破れている。** 本書はこれを構造的に立て直す。

## 区分の基準

| 区分 | 基準 |
|---|---|
| **major** | 既存の保存データ・設定が使えなくなる変更(settings.json を読めない/DB を開けない/エクスポート JSON の後方非互換) |
| **minor** | 利用者から見てできることが増える、**または分析結果の数値が変わる**変更 |
| **patch** | それ以外(不具合修正・内部改善・CI/文書のみ) |

「数値が変わる」を minor に含めるのは本リポジトリ特有の判断である。スコアリング(バイアス補正・EV計算)の
変更は「機能が増える」わけではないため機能追加とは言えないが、利用者は「前回と結果が違う」と気づく。
これを patch(=「気にしなくてよい変更」)に埋もれさせると、過去の分析結果との比較が版数だけでは
判断できなくなる。そのため minor 側に寄せる。

## 上げる主体とタイミング

- **主体**: オーケストレーター(プロジェクトマネジメント役)。
- **タイミング**: boss 承認後、承認印 `[PUBLISH-APPROVED]` を付ける最終コミットで上げる
  (`CLAUDE.md` 手順6)。
- **頻度**: **新しい内容を配布する公開1回につき必ず1回上げる。** ここでいう「公開」とは、
  package.json の変更を含む新規コミットに承認印 `[PUBLISH-APPROVED]` を付けて push し、
  dev-latest を更新することを指す。**`workflow_dispatch`(手動実行)による同一コミットの再送は
  「公開」に含めない。** コミットそのものが同一である以上、版数を上げる対象(新規コミット)が
  そもそも存在しない——つまり版数は上げない/上げられない(この結論はコミットの引用に依存せず
  単独で成立する)。参考として、CI の偶発失敗から再実行・再送で回復すること自体は本リポジトリで
  正当な運用として実績がある(例: `0882e77`「CI再実行」、`0bee388`「再送」)。ただしこの2件は
  いずれも新規コミット(差分ゼロ/コメントのみ)による再送であり、`workflow_dispatch` による
  同一コミット再送そのものの実例ではない(`workflow_dispatch` は git 上に新規コミットを作らない
  ため、ローカルの git 履歴だけでは過去の実行例を直接検証できない)。ここでは「失敗からの
  再実行・再送は正当な運用である」という一般論の裏付けとして引用している。#45(D-2)の機械検査でも
  同じ理由で `workflow_dispatch` を版数据え置き検査から除外している(#45 で実装済み。
  `.github/workflows/build-windows.yml` の版数据え置き検査ステップの `if:` に
  `github.event_name == 'push'` を含める形で、`scripts/release-gate.ts` の
  `version-bump-check` サブコマンドを workflow_dispatch 実行時にはスキップする)。
  人に残る判断は「major/minor/patch のどれか」だけであり、「上げるか上げないか」は
  判断させない(判断させると 1.1.0 が 94 コミット据え置かれた事故が再発するため)。

### 版数を上げるときの同時更新チェックリスト

版数を上げる際は、以下をすべて同時に更新する。**一つでも更新を忘れると `pnpm test`
(`packages/app/test/version-policy.test.ts`)が失敗する。この失敗は「テストが壊れている」の
ではなく「更新漏れをテストが正しく検出している」と読むこと。**

1. root `package.json` の `version`
2. `packages/app/package.json` の `version`
3. `docs/current-spec.md` の冒頭(「実際に実装されている現状(vX.Y.Z)」の箇所)
4. `docs/current-spec.md` のバージョン一覧行(「バージョン: ルート/アプリ `X.Y.Z`」の箇所)
5. `keiba-ev-tool-spec.md` の冒頭(「実装は vX.Y.Z に到達しており」の箇所)
6. `packages/app/test/version-policy.test.ts` の `EXPECTED_APP_VERSION` 定数。**あわせて同ファイルの
   テスト名に埋まっている版数 literal も直す**(定数だけを見て置換すると取り残す)
7. 本書に「次の正式版が X.Y.Z である根拠セクション」(`## 次の正式版が X.Y.Z である根拠`という
   見出し)を追加する(区分〈major/minor/patch〉の判断根拠を残す)
8. `scripts/test/release-gate.test.ts` の実プロセス起動テスト(AC8)が持つ版数 literal。
   **対象は2つのテストだが、書き換える literal は4つある**(「前提: …の version が X.Y.Z である」の
   テスト名と `expect(appPkg.version).toBe("X.Y.Z")`、「バージョン一致(vX.Y.Z)で終了コード0」の
   テスト名と `"vX.Y.Z"` 引数)。**「2箇所」を「2つの文字列」と読んで機械置換すると取り残す**
   (1.3.1 への版上げ時に boss の実測で判明。取り残しても `pnpm test` が落ちて検出される)

6 と 8 は上げた先の版数を実ファイルに直接ピン留めしている。これ自体は「是正が実際に行われたことの
直接検証」であると同時に、次の上げ忘れに対する意図的な摩擦として機能する。摩擦として残すからには、
その存在をこの操作者向け文書に明記する(このチェックリストがその対)。

**8 は 1.2.2 への版上げで初めて露見した抜けである**(#45 で AC8 の実プロセステストを追加した際、
このチェックリストへの追記が漏れていた)。テストが落ちて発覚したので実害は無かったが、
「チェックリストに載っていない版数 literal」が今後も増えうることの実例として記録しておく。

7 は `packages/app/test/version-policy.test.ts` の `hasVersionRationaleSection` によって、
`EXPECTED_APP_VERSION` に対応する見出しの存在が機械的に検査される(code-reviewer 一次レビューの
提案を一般化して採用。literal な版数を直接ピン留めする専用テストを版ごとに積み上げるのではなく、
汎用の不変条件にすることで「根拠を書く」こと自体を機械的に強制する)。

## 表記ルール

- **プレリリース識別子は使わない。** `X.Y.Z` のみを使う(`1.2.0-dev.1` のような識別子・
  `1.2.0+build.5` のようなビルドメタデータは付けない)。
- **`packages/core`(`@keiba/core`)は運用対象外・据え置き。**
- **root と app の版数は常に一致させる。**
- **正式版タグは `v<package.json の version>`**(例: `v1.2.0`)。

## なぜコミットメッセージ規約による自動判定を採らないのか

「機能追加か否か」をコミットメッセージやパスから自動判定する案(Conventional Commits 等)は
**採らない**。本リポジトリのコミットメッセージは日本語の自由記述であり、`機能D-2c第4段`・
`core/app:`・`CI:`・`レビュー観点:` のような多様な書き出しが既に混在している。決まった接頭辞
(`feat:`/`fix:` 等)を要求する運用は、94 コミット分の既存の書き方と、3体のサブエージェント
(tdd-implementer / code-reviewer / boss)の指示書をすべて書き換えるコストを要し、しかも自由記述の
実態がある限り誤判定(feat のつもりが fix と書かれる/その逆)は避けられない。コストに見合わないため
自動判定は採用しない。代わりに、#43 で機械的に一意になった「公開の瞬間」に紐づけ、区分の判断だけを
人に残す方式を選んだ。

## なぜ core を対象外にするのか

`packages/core`(`@keiba/core`)は `package.json` に `"private": true` を持ち、npm には公開して
いない。app からの参照は `"@keiba/core": "workspace:*"`(`packages/app/package.json`)のみであり、
pnpm workspace 内でシンボリックリンク解決されるため、`workspace:*` という指定自体が固定バージョンでの
依存解決を必要としない。つまり core の `version` フィールドはどの値であっても app のビルド・実行に
一切影響しない。exe のファイル名にも現れない(現れるのは app の version のみ)。上げても下げても
意味を持たない値を運用対象に含めると「上げ忘れ」の検知対象が無意味に増えるだけなので、対象外・
据え置き(現状 `0.2.0`)とする。

## 次の正式版が 1.2.0 である根拠(本タスクでの是正)

1.1.0 以降に入った変更は以下の通り機能追加であり(minor 相当)、破壊的変更(major 相当)は無い:

- 組み合わせオッズ取得(D-2b)・券種横断の予算配分(D-2c 第1〜4段)・確率の質の計測基盤——
  いずれも利用者から見て「できることが増える」変更。
- 破壊的変更が無いことは実測済み: 設定は `packages/app/src/main/settings-store.ts` の
  `coerceSettings(raw: unknown)` が既定値マージで検証するため、旧い `settings.json`
  (新フィールドを持たない)もそのまま読める。DB は `packages/core/src/ev/analysis-store.ts` の
  `migrateResultPayoutColumn` 等(`ALTER TABLE ... ADD COLUMN` による後方互換マイグレーション、
  既存行は NULL として読める)により、旧バージョンで作成済みの DB もそのまま開ける。

よって 1.1.0 → **1.2.0**(minor)が妥当と判断した。

## 次の正式版が 1.2.1 である根拠(Issue #45 での是正)

Issue #45 の変更は `.github/workflows/build-windows.yml`・`scripts/release-gate.ts`・
テスト・文書のみであり、`packages/app/src`・`packages/core/src` には一切触れていない。
上記の区分の基準に照らすと「利用者から見てできることが増える」「分析結果の数値が変わる」の
どちらにも該当せず、区分の基準表に従い **patch** が妥当である。

据え置きではなく実際に上げる理由: `dev-latest` には既に `keiba-ev-tool-1.2.0-portable.exe` が
公開済みであり、本タスク自身が新設する版数据え置き検査(`version-bump-check`)は、今回ビルドする
exe と同名のアセットが既に存在する場合に block する。版数を据え置いたまま本タスクの変更を
承認印付きで push すると、この検査自身が発火してジョブが失敗する。したがって 1.2.0 → **1.2.1**
(patch)への是正は、本タスクの変更を公開するための前提条件であると同時に、新ゲートが
正当な公開(=版数を上げた公開)を妨げないことの allow 経路の実地証明にもなっている。

## 次の正式版が 1.2.2 である根拠(Issue #31 での是正)

Issue #31 の変更は `packages/core/src/ev/`(`allocation-primitives.ts` に述語 `isUsableOdds` を新設し、
`bet-allocation.ts` の候補フィルタと `combo-bet-allocation.ts` の2箇所が委譲)とそのテスト・JSDoc のみで、
`packages/app/src` には触れていない。

**patch である根拠は「利用者から見た挙動が変わらない」ことではなく、「実データで数値が動かない」ことである。**
本修正は不正なオッズ値を持つ馬を候補から外す挙動変更を含むが、`placeOddsMin` に非有限値が入る到達経路は
現状存在しない(生成箇所は `expected-value.ts` の2箇所のみで、いずれも厳格な検証を通る)。したがって
実運用のどのレースでも配分結果は1円も変わらない。区分表の「**分析結果の数値が変わる**」(minor)には
該当せず、「それ以外(不具合修正・内部改善)」に当たる。

よって 1.2.1 → **1.2.2**(patch)が妥当と判断した。

なお本修正は**潜在的欠陥の是正**であり、到達経路のある実害の修正ではない。将来 `placeOddsMin` に
非有限値を書き込む経路ができた場合、この修正が初めて実データに効く。

## 次の正式版が 1.3.0 である根拠(Issue #15 での変更)

Issue #15 は、混在配分の買い目一覧を**上位20件の常時表示+残りの折りたたみ**に分ける変更である
(`packages/app/src/renderer/mixed-allocation-view.ts` の `splitAllocationsForDisplay` と、
`BatchAnalysisView.tsx` の描画)。

**minor である根拠**: これは**意図的な UI 挙動変更**であり、区分表の patch(「それ以外(不具合修正・
内部改善・CI/文書のみ)」)に当たらない。ただし「利用者から見てできることが増える」という説明は
**正確ではない** — 既定で表示される買い目はむしろ**減り**、代わりに展開操作が**増える**。
増減の向きにかかわらず、利用者が見る画面の既定の姿が変わる変更なので minor に置く。

**「分析結果の数値が変わる」には該当しない**: 配分計算(`packages/core/src/ev/**`)には1行も
触れておらず、`totalStake`・券種別内訳・注記はいずれも分割の前後で同一である(不変式1〜3として
テストで固定した)。変わったのは**画面に何行出すか**だけである。

## 次の正式版が 1.3.1 である根拠(Issue #52 での変更)

Issue #52 は、レース結果ページからワイド・三連複の**確定払戻を取り込んで永続化**する変更である
(`packages/core/src/scraper/parse-race-result.ts` の `parseComboPayoutRow` と、
`packages/core/src/ev/analysis-store.ts` の `race_combo_payouts` / `race_combo_payout_imports`)。

**patch である根拠**: 区分表の minor は「**利用者から見てできることが増える**」または
「**分析結果の数値が変わる**」だが、本変更は**どちらにも該当しない**。UI・IPC は一切触っておらず
(過去分析の再表示は #55 がスコープ)、`ev/verify.ts` も無改変なので**回収率を含む分析結果の数値は
1つも変わらない**。取得・永続化という内部能力は増えるが、**利用者からは観測できない**。
よって区分表の patch(「それ以外(不具合修正・内部改善・CI/文書のみ)」)に該当する。

**major でない根拠**: 新テーブルは `CREATE TABLE IF NOT EXISTS` の追加のみで、旧DBはそのまま開けて
既存データも読める(旧DB互換をテストで固定済み)。「既存の保存データ・設定が使えなくなる変更」に
当たらない。

なお本 Issue は**保存はするが検証(`ev/verify.ts`)には一切反映しない**という中間状態で着地している。
反映は #54 が担う。`docs/current-spec.md` の「記録・回収率検証: 複勝のみ」は本 Issue 完了時点でも
**まだ正**であり、その微妙な状態を同文書に明記した。

## 公開後の確認(版数据え置き検査が実際に走ったことの確認)

承認印付き push のあとは、CI run の「版数据え置きを検査(dev-latest 公開前)」ステップのログを必ず見る。
`版数据え置き検査: 問題ありません(公開を続行します)` が出ていれば、dev-latest の現行アセットとの比較が
実際に行われている。代わりに `::warning::` が出ている場合(設定不備・API 取得失敗)は、この検査は
fail-open でスキップされており版数据え置きを検出できていない(`scripts/release-gate.ts` の設計)。
exe が更新されたという事実だけでは「比較して問題なかった」のか「比較できずに素通りした」のかを
区別できないため、この確認は省略しない。
